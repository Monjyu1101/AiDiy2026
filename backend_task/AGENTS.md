# backend_task 実装概要

## 本書の目的

このファイルは `backend_task` の構成、提供 API、実装入口を示す概要ドキュメントです。
AI エージェントは、本書に個別手順や一時的な作業メモを追記しないでください。
コアシステム機能調整は `../.aidiy/knowledge/_index.md` を入口にします。

## 概要

`backend_task` はポート `8093` 上で動作する **AIタスク実行 + 定期タスク** の FastAPI 常駐サーバーです。
`backend_server/apps_main.py` 起動後にルート `_start.py` から起動されます。

- Backend: FastAPI + uvicorn（Python 3.13+、uv 管理）
- 起動: `uvicorn task_main:app --host 0.0.0.0 --port 8093`
- DB: `backend_server/_data/AiDiy/database.db` を共有（`Aタスク要求` / `Aタスク明細` / `Aタスク実行条件` テーブル、`Aチーム依頼`・`Aチーム作業`・`Aチーム状況`も更新）
- 新規タスクID: `C採番`（採番ID=`Aタスク要求`、初期値1000）による`TK`＋8桁連番（例: `TK00001001`）
- 定期処理: 60 秒間隔のハートビートログ + 5 秒間隔の AIタスク監視ループ（明細起動） + 10 秒間隔の実行開始条件監視ループ（発火確認とタイムアウト確認は hh:mm 変化時＝毎分、`Aチーム状況`の再集計は毎回）
- タイムアウト: `Aタスク要求`は進捗が止まってからの経過で判定し、`準備中`＝`task_sub/sub_init.py`による明細分解の最中は10分、それ以外は30分。`Aタスク明細`は開始日時から30分
- 再起動: `backend_task/temp/reboot_task.txt` 検知で終了し、ルート `_start.py` 起動中なら自動再起動

## AIタスク実行の流れ

1. フロントエンド（frontend_web `/AIタスク` 画面 / frontend_avatar タスクウィンドウ）が `/task/タスク要求/AI登録` で要求を仮登録（準備開始）する。
2. 監視ループ（5秒間隔）が`準備開始`かつPID未設定の仮登録を検出し、`準備中`へ更新してから`sub_init.py`サブプロセスで要求をAI分解し、`Aタスク明細`を生成する。
3. 先行 SEQ が完了した未実行明細を `sub_proc.py` で 1 ステップずつ実行する（Code CLI = `TASK_AI_NAME` / `TASK_AI_MODEL`、開始 / 終了明細は `sub_start.py` / `sub_terminate.py`）。
4. code agent 実行中は原則直列。軽量明細のみ並行起動を許可。実行回数上限（3 回）超過で失敗にする。
5. 実行開始条件（`Aタスク実行条件`: 時間指定 / 間隔実行 / 定時実行 / フォルダ変化）付きのタスクは本登録後 `準備完了` で待ち、監視ループが毎分（hh:mm 変化時）次回実行日時と条件を確認して、成立時に明細 → 要求の順で `待機` に戻して実行する。対象は要求が `準備完了` / `完了` かつ明細が全件待機または全件完了のタスクのみ（実行途中は開始しない）。次回実行日時は発火可能状態（実行有効 かつ 要求が `準備完了` / `完了`）の間だけ保持し、それ以外は空にする（実行条件の編集・実行有効切替・起動時も同じルールで再計算 = `tasks_watcher.実行条件再計算`）。即時（条件なし）は本登録で直接 `待機` になる。

タスクフローの特徴:

- カンバン方式ではなく、`先行SEQ`（カンマ区切りで複数指定可）による依存定義の DAG。
- 垂直の直列フローだけでなく、水平の並行分岐を自由に組める。
- 実行可能判定は「先行 SEQ が全て完了」（`tasks_db.実行可能明細一覧`）で、依存が満たされた明細から実行する。
- フロー図（frontend の `AIタスク_フロー図.vue`）は最長経路 = クリティカルパス基準で列を配置して進行を可視化する。

`TASK_AI_NAME` の有効値は Code AI と同じ（`claude_sdk` / `claude_cli` / `copilot_cli` / `codex_cli` / `antigravity_cli` / `opencode_cli` / `aidiy_hermes`）です。

## AIチームとの連携

`Aチーム依頼`（backend_team）経由で投入された`Aタスク要求`は、タスクIDが一致する`Aチーム依頼`行を持ちます。
`sub_start.py` / `sub_proc.py` / `sub_terminate.py` が呼ぶ明細完了系API（`tasks_db.明細完了` / `開始明細完了` /
`終了明細完了` / `明細再試行` / `明細失敗`）は、状態・応答タイトル・応答内容を該当する`Aチーム依頼`行にも
同一トランザクションで反映する（`tasks_db._Aチーム依頼反映`）。既に`エラー`の`Aチーム依頼`行は上書きしない
（`明細失敗`のエラー化と`明細再試行`のエラーからの復帰は例外）。

同じ反映で、作業ループ（PDCA）から投入されたタスクは`Aチーム作業`にも書き戻す（`tasks_db._Aチーム作業反映`）。
`Aチーム作業`は依頼IDで結合し、`状況`（Aチーム依頼の状態を写した表示用の値）・`終了日時`・`応答内容`を更新する。
完了時は経験生成を待つため`終了日時`を空のままにし、経験本登録時にbackend_teamが`状況=済`として終了させ、生成結果を`まとめ内容`へ保存する。元の応答内容は保持する。エラーでは`終了日時`を入れ、再試行で`実行中`へ戻るときは空に戻す。backend_teamが次のPDCA段へ進めるかを見るのは
`状況=済`への更新と同時に設定される`終了日時`のため、経験本登録前にここを更新すると作業ループが先行してしまう。`Aチーム作業`やその`状況`列が未作成
（旧backend_team）の場合は何もしない。

明細完了系API以外に、次の3つも`Aチーム依頼`・`Aチーム作業`へ反映する。ここで反映しないと
`Aチーム依頼`が実行中、`Aチーム作業`が未終了のまま残り、作業ループ（PDCA）が次の段へ進めなくなる。

- システム再起動時のクリーンアップ（`tasks_db.PID全クリア`）。PIDを持つのは明細だけで要求は
  `実行中`・PID空という状態があるため、明細にPIDがあったタスクの要求も未終了ならまとめて終わらせる
- 無進捗タイムアウト（`tasks_db.タイムアウト対象エラー化`）
- 画面からの状態変更（`tasks_db.タスク要求更新登録`）。`準備開始`はチーム側も`準備中`へ戻して未終了に、
  `完了`/`済`/`エラー`/`中止`は終了日時を打刻する。人の判断を優先するため通常のエラーガードは外す

タイムアウト判定の起点はテーブルごとに違う。`Aタスク明細`は開始日時（1ステップ＝1プロセスの実行）、
`Aタスク要求`は開始日時と更新日時の新しい方を使う。要求の開始日時は最初の明細が終わった時点で入ったきり
更新されないため、開始日時だけで見ると全ステップの合計時間に制限をかけることになり、正常に進んでいる
長いタスクまで打ち切ってしまう。更新日時は明細を1つ終えるたびに動くので、進捗が続く限り対象にならない。

制限分も使い分ける。`Aタスク要求`が`準備中`（`sub_init.py`による明細分解の最中）は`準備タイムアウト分`
（既定10分）、それ以外と`Aタスク明細`は`実行タイムアウト分`（既定30分）。分解は明細を作るだけの短い処理で、
長引くのは応答待ちで固まっている場合だから短く見る。

`Aチーム状況`は、実行開始条件の監視ループ（10秒間隔）の最後に毎回、有効なAチーム要員ごとに実行有効な
Aタスク要求（更新日時が24時間以内）と、開始日時あり・終了日時なしのAチーム経験を集計して作り直す（`tasks_db.チーム状況更新`）。
経験は要員別の最終更新日時も保持し、backend_teamが待機中要員の雑談・休憩エリア切替間隔を更新秒の一桁（0は10分）から決める。
書き込みはbackend_task側のみで、backend_teamは読み取り専用で参照する。

## 提供 API

すべて `/task` 配下、CRUD 系は POST 統一・`{"status", "message", "data"}` 形式です。

| エンドポイント | 役割 |
|----------------|------|
| `GET /`、`GET /health` | 稼働状況、ヘルスチェック |
| `POST /task/タスク要求/一覧` / `最大更新日時` | タスク要求の一覧、ポーリング用最大更新日時 |
| `POST /task/タスク要求/AI登録` / `登録` / `更新登録` / `本登録` | 要求の仮登録（準備開始）、更新（再分解）、AI 分解結果の確定。AI登録の`タスクID`は省略時に自動採番、`プロジェクト` / `TASK_AI_NAME` / `TASK_AI_MODEL` は未指定（null）のとき要求編集ダイアログ新規時と同じ条件（利用者IDの更新最終レコードの値 → 無ければ規定値）で補完 |
| `POST /task/タスク要求/有効切替` / `AI失敗` | 有効フラグ切替、AI 分解失敗の記録 |
| `POST /task/タスク明細/一覧` / `最大更新日時` | タスク明細の一覧、ポーリング用最大更新日時 |
| `POST /task/タスク明細/更新登録` / `有効切替` / `完了` / `失敗` / `全消去` | 明細の編集、有効切替、実行結果の記録 |
| `POST /task/タスク実行条件/取得` | 要求に紐づく実行開始条件の取得（登録は AI登録 / 更新登録 に同梱）。キーはタスクIDのみ |

**CRUD のキーはタスクID単独です。** `Aタスク要求` / `Aタスク実行条件` はタスクIDが主キー、
`Aタスク明細` は（タスクID, 明細SEQ）が主キーです。利用者IDは所有者を表す属性で、一覧の絞り込みには
使いますが、取得・更新・削除の条件には使いません。更新系リクエストの `利用者ID` は互換のため
省略可で受け取るだけで、キーとしては無視します（所有者として記録するのは `AI登録` の新規登録時と、
仮登録が無い場合の `本登録` だけ）。これにより、管理者が全ユーザー表示で他利用者のタスクを
編集しても対象を見失うことがありません。

`Aタスク実行条件` は旧版で主キーが（利用者ID, タスクID）の複合でした。`tasks_db.初期化()` が
旧スキーマを検出したときだけタスクID主キーへ作り替えます（重複タスクIDは更新日時が新しい行を残す）。
| `POST /task/プロジェクト選択肢` | 要求編集ダイアログのプロジェクト候補 |

## ファイル構成

| パス | 役割 |
|------|------|
| `task_main.py` | 軽量な FastAPI エントリポイント。ログ初期化と app 生成だけを担当 |
| `task_proc/app.py` | FastAPI アプリ生成、ルーター登録、lifespan / reboot watcher の接続 |
| `task_proc/routes.py` | `GET /`、`GET /health` の API ルーター |
| `task_proc/runtime.py` | ハートビート、`reboot_task.txt` 監視、AIタスク監視ループの起動 |
| `task_proc/tasks_api.py` | `/task/タスク要求/*`、`/task/タスク明細/*` の API ルーター |
| `task_proc/tasks_db.py` | `Aタスク要求` / `Aタスク明細` / `Aタスク実行条件` テーブルの sqlite3 直接アクセス |
| `task_proc/tasks_watcher.py` | 5 秒間隔の監視ループ。sub_* サブプロセスの起動と状態遷移 |
| `task_sub/sub_init.py` | 要求を AI 分解して明細を生成するサブプロセス |
| `task_sub/sub_start.py` / `task_sub/sub_proc.py` / `task_sub/sub_terminate.py` | 開始明細 / 1 ステップ実行 / 終了明細のサブプロセス |
| `_start.py` | 単体起動、およびルート `_start.py` からの起動委譲先 |
| `_setup.py` | `uv sync --upgrade` による依存関係セットアップ |
| `_cleanup.py` | `.venv` / `temp` / Python キャッシュの削除 |
| `pyproject.toml` | uv 依存定義 |

## フロントエンドからの利用

- frontend_web / frontend_avatar とも Vite proxy `/task/*` → `http://127.0.0.1:8093` 経由で呼び出す（avatar は `taskClient`、Electron 本番は 8093 直結）。
- 画面は frontend_web `src/components/AIタスク/`、frontend_avatar `src/components/AIタスク/`（Electron は task1〜task3 ウィンドウ + taskDialog）。

## セットアップ・起動

```bash
cd backend_task && uv sync --upgrade
cd backend_task && uv run uvicorn task_main:app --reload --host 0.0.0.0 --port 8093
```

ルートから起動する場合は `python _start.py` を使います。
起動順は `backend_server/apps_main.py` の後です。
