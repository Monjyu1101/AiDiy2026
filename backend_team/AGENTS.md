# backend_team 実装概要

## 本書の目的

このファイルは `backend_team` の構成、提供 API、実装入口を示す概要ドキュメントです。
具体的な起動・検証手順は `.aidiy/knowledge/` に集約します。
AI エージェントは、本書に一時的な作業メモを追記しないでください。

## 概要

`backend_team` はポート `8094` 上で動作する、複数AIエージェントの継続活動を管理する FastAPI サーバーです。
現段階はUI検討用の仮実装です。要員マスタとチーム作業は共有SQLiteへ保存し、活動状態はインメモリ管理です。

- 設定: `backend_server/_config/AiDiy_key.json` の `TEAM_BASE`、`TEAM_AI_NAME`、`TEAM_AI_MODEL`、`TASK_AI_NAME`、`TASK_AI_MODEL`
- 初期ポート: `8094`
- 起動: `uvicorn team_main:app --host 0.0.0.0 --port 8094`
- DB: `backend_server/_data/AiDiy/database.db` の `Aチーム要員` / `Aチーム作業` / `Aチーム目標` / `Aチーム経験` / `Aチーム改善` / `Aチーム状況`（`Aチーム状況` は読取専用、backend_task側が更新。`Aチーム改善` の終了日時・応答内容もbackend_task側が更新）
- 状態: エージェント、活動履歴、シミュレーション有効状態（作業中・瞑想中・雑談中・休憩中）。Aチーム状況と経験更新時刻から決定
- 定期処理: 8秒間隔のエージェント状態更新 + 5秒間隔の`Aチーム作業`監視 + 1分間隔の`Aチーム経験`生成と`Aチーム改善`（回収・改善ループ）確認（無進捗タイムアウト確認と同じ毎分ゲート）
- タイムアウト: 進捗が止まってからの経過で判定する（総実行時間の上限ではない）。`Aチーム作業`が`準備中`＝`team_sub/sub_init.py`による担当選択とAIタスク投入の最中は10分、それ以外は30分
- 再起動: `backend_team/temp/reboot_team.txt`

## 提供 API

| エンドポイント | 役割 |
|----------------|------|
| `GET /`、`GET /health` | 稼働状況 |
| `POST /team/状態/取得` | チーム全体のスナップショット |
| `POST /team/設定/取得` | `CODE_BASE_PATH`とTeamAI設定の取得 |
| `POST /team/エージェント/一覧` | エージェント一覧 |
| `POST /team/エージェント/召喚` | persona値で`Aチーム要員`をupsertして有効化 |
| `POST /team/エージェント/排除` | `Aチーム要員`の行を残して無効化 |
| `POST /team/エージェント/会話` | personaをシステム指示へ設定し、選択したプロジェクトと`TASK_AI_*`で`aidiy_code_agents`へ単発会話を同期依頼（最大3分、履歴保持なし） |
| `POST /team/エージェント/状態変更` | 状態、作業内容、ひとことの変更 |
| `POST /team/活動/一覧` | 活動履歴 |
| `POST /team/シミュレーション/切替` | 自動行動の開始・停止 |
| `POST /team/召喚要員/一覧` | `persona/` の有効なフォルダ名を召喚候補として取得 |
| `POST /team/要員/一覧` / `取得` | `Aチーム要員` の参照 |
| `POST /team/要員/登録` / `変更` / `削除` | `Aチーム要員` の保守 |
| `POST /team/作業/一覧` / `取得` / `最大更新日時` | `Aチーム作業` の参照（直近30日・最大100件）と5秒ポーリング用更新確認。画面は最大更新日時が変わったときだけ一覧を再取得する |
| `POST /team/作業/登録` / `変更` | `Aチーム作業` の追加・編集。登録の`プロジェクト` / `TEAM_AI_*` / `TASK_AI_*` は未指定（null）のとき作業編集ダイアログ新規時と同じ条件（要員IDの更新最終レコードの値 → 無ければ規定値）で補完 |
| `POST /team/経験/一覧` / `最大更新日時` | `Aチーム経験` の参照（`プロジェクト`・`要員ID`で絞り込み、最大100件、完了日時の新しい順）と5秒ポーリング用更新確認。経験値合計も返す |
| `POST /team/経験/取得` | `Aチーム経験` 1件の参照 |
| `POST /team/経験/本登録` / `失敗` | `team_sub/sub_exp.py` からの結果反映（完了 / エラー） |
| `POST /team/改善/一覧` / `最大更新日時` | `Aチーム改善` の参照（`プロジェクト`で絞り込み、最大100件、改善IDの新しい順）と5秒ポーリング用更新確認 |
| `POST /team/目標/一覧` / `最終` / `取得` | `Aチーム目標` の参照。`最終` は更新日時が最新の 1 件（チーム空間の掲示板に表示） |
| `POST /team/目標/保存` / `削除` | `Aチーム目標` の登録・変更（CODE_BASE_PATH 単位の upsert）と削除（`../` は削除不可）。チーム目標・改善ループON/OFF・パターンのいずれかの変更時だけ、そのパスの `Aチーム改善` をクリアする。最大ループ回数・動員要員数だけの変更ではクリアしない |
| `POST /team/状況/一覧` / `最大更新日時` | `Aチーム状況` の参照（要員ごとのAタスク要求集計）。待機・実行は実行有効な要求、完了・エラーは実行有効に関係なく直近24時間の要求を数える。画面は5秒ごとに最大更新日時を確認し、変化時だけ一覧を再取得する |

レスポンスは `status`、`message`、`data` の統一形式です。

## Aチーム要員

| 項目 | 内容 |
|------|------|
| `要員ID` | 主キー |
| `要員名` | 表示名 |
| `役割` | チーム内の担当 |
| `人格情報` | 口調、行動方針、性格など |
| `有効` | 稼働対象フラグ |
| 監査8項目 | 登録・更新の日時、利用者ID、利用者名、端末ID |

初期データは `要員ID=admin`、`要員名=admin`、`有効=1` の1件です。初期投入は冪等で、既存値を上書きしません。
persona要員は召喚時に `persona.json` の現在値でupsertし、排除時は行を削除せず `有効=0` にします。
`admin` は削除・無効化・排除できません。

## Aチーム作業

`Aタスク要求`に対応するAIチーム用の作業台帳です。主キーは`作業ID`単独です（`要員ID`は列として保持）。
新規作業IDは`C採番`（採番ID=`Aチーム作業`、初期値1000）による`TW`＋8桁連番（例: `TW00001001`）です。
追加経路はフロントエンド（`/AIチーム` 画面）と `aidiy_team_agents`（backend_tools の MCP）の 2 つで、どちらも `POST /team/作業/登録` を使います。

| 項目 | 内容 |
|------|------|
| `作業ID` | 主キー |
| `要員ID` | 作業を保有する要員 |
| `プロジェクト` / `タイトル` / `要求内容` | 作業の依頼内容 |
| `TEAM_AI_NAME` / `TEAM_AI_MODEL` | AiDiy ルート（`../`）で行うチーム管理処理（担当選定、結果JSON整形）に使用するAI設定 |
| `TASK_AI_NAME` / `TASK_AI_MODEL` | 対象プロジェクトフォルダで行う作業実行・経験整理に使用するAI設定 |
| `実行有効` / `状態` | 実行可否と`準備開始`・`準備中`・`準備完了`・`待機`・`実行中`・`エラー`・`完了`・`済`・`中止` |
| `PID` / `開始日時` / `終了日時` / `実行回数` | 実行管理項目 |
| `タスクID` | `aidiy_task_agents`へ投入した`Aタスク要求`のID |
| `応答タイトル` / `応答内容` | AIタスクの作業結果 |
| `まとめ内容` | 経験生成後に`Aチーム経験.まとめ内容`を複写する内容 |
| 監査8項目 | 登録・更新の日時、利用者ID、利用者名、端末ID |

## Aチーム経験

完了した作業から得た経験を蓄える台帳です。主キーは`経験ID`（`C採番`の採番ID=`Aチーム経験`、初期値1000、`TE`＋8桁）で、
`作業ID`は UNIQUE です（1作業＝1経験。未登録判定にも使う）。

| 項目 | 内容 |
|------|------|
| `経験ID` | 主キー。`TE`＋8桁連番 |
| `作業ID` | 元の`Aチーム作業`（UNIQUE） |
| `タスクID` / `要員ID` / `プロジェクト` | 経験のもとになった`Aタスク要求`、**実行した本人**（`Aタスク要求`の`利用者ID`。`Aチーム作業`の`要員ID`＝依頼元ではない）、CODE_BASE_PATH（一覧の絞り込みキー） |
| `タスクタイトル` / `要求内容` / `実行応答内容` / `完了日時` | 仮登録時に`Aタスク要求`から複写する表示用の値（何を・要求・応答・いつ完了したか）。一覧とダイアログはこのテーブルだけで描画できる |
| `タイトル` / `経験値` / `分類` / `まとめ内容` / `学び` | AI が出力した経験値（`経験値`は1〜100の整数、`分類`は実装/調査/修正/検証/運用/その他） |
| `状態` | `生成中` / `完了` / `エラー` |
| `PID` / `開始日時` / `終了日時` / `エラー内容` | 生成プロセスの管理項目（`開始日時`・`終了日時`は経験生成の開始と終了） |
| 監査8項目 | 登録・更新の日時、利用者ID、利用者名、端末ID |

生成の流れ（1分ごとの処理）:

1. `Aチーム作業`が`状態=完了`かつ`更新日時`が1時間以内、紐づく`Aタスク要求`も`状態=完了`、
   `Aチーム経験`に同じ`作業ID`が未登録のものを対象にする。
2. `開始日時`だけ入れた仮登録（`状態=生成中`、`PID=CLAIM`）を作り、`team_sub/sub_exp.py`を起動して PID を記録する。
3. `sub_exp.py`は`backend_task`から`AIタスク明細`を取得し、対象プロジェクトのパスで `TASK_AI_NAME / TASK_AI_MODEL` の AI に経験値をまとめさせ（第1ステップ）、
   AiDiy ルート（`../`）で `TEAM_AI_NAME / TEAM_AI_MODEL` の AI に JSON を`temp/exp/output/<経験ID>.json`へ書かせる（第2ステップ）。
   検証後に`/team/経験/本登録`へ書き戻す。本登録と同時に元の`Aチーム作業`を`済`へ変更して`まとめ内容`へ複写し、対応する`Aチーム改善`も`状況=済`・`まとめ内容`へ複写して終了させる。元の応答内容は保持する。失敗時は`/team/経験/失敗`でエラーにする。

蓄積した経験は担当割当にも使います。`team_sub/sub_init.py`が担当要員を AI に選ばせるとき、
`team_exp_db.要員別経験概要()`（要員ごとの経験値合計・件数・直近の経験のタスクタイトル／分類／学び）を
プロンプトへ渡し、似た経験を持つ要員へ寄せるよう指示します（同じ担当者に集めてナレッジを再利用する）。
対象プロジェクトの経験が無ければ全プロジェクトの経験で判断し、取得に失敗しても選択自体は続行します。

生成が30分を超えたものは毎分の確認でエラーにし、システム再起動時は`生成中`をすべてエラーにします。

フロントエンド（`/AIチーム` 画面の経験一覧）は、掲示板に出ているプロジェクトの経験だけを
「何を（タスクタイトル）／誰が（要員ID）／完了日時」で表示し、行のダブルクリックで
要求内容・応答内容・まとめ内容を共通の要求応答ダイアログに出します。

## Aチーム目標

`CODE_BASE_PATH`（プロジェクトのパス）ごとにチーム目標を 1 件保持します。主キーは `CODE_BASE_PATH` です。
起動時に 1 件も無ければ `../` = 「よく考えて、行うべきことを実行する。」を投入します（既存値は上書きしません）。

| 項目 | 内容 |
|------|------|
| `CODE_BASE_PATH` | 主キー。プロジェクトのパス |
| `チーム目標` | そのパスで共有する目標文 |
| `改善ループ` | 目標に向けた改善ループを回すかどうか（`0`=オフ / `1`=オン、既定は `0`） |
| `最大ループ回数` | PDCAを完了する上限回数（1〜99、既定は1）。`99`は無制限 |
| `動員要員数` | `S`（相談）へ動員する要員数（1〜99、既定は2）。実際の動員は admin 以外の有効要員数が上限で、画面の選択肢もその人数まで |
| `パターン` | 改善ループの段構成。`SPDCA`=S→P→D→C→Aの5段 / `PlanDo`=P→Dの2段（既定） |
| `更新連番` | 保存ごとの連番。更新日時が秒単位のため、同じ秒に複数保存されたときの順序決定に使う |
| 監査8項目 | 登録・更新の日時、利用者ID、利用者名、端末ID |

フロントエンド（`/AIチーム` 画面）は更新日時が最新の 1 件を、上空を旋回する飛行船が吊り下げる掲示板に表示し、
掲示板クリックで保守ダイアログ（登録済パス一覧 + パス選択・パス入力・目標入力・改善ループ・最大ループ回数・動員要員数・パターン）を開きます。
目標文・改善ループON/OFF・パターンのいずれかを変更した場合だけ既存の改善記録をクリアします。最大ループ回数だけを1から2へ
増やした場合などは履歴を保持し、完了済み回数に追加して残りのサイクルを実行します。

## Aチーム改善（PDCAサイクル）

`Aチーム目標` の `改善ループ` がオンのプロジェクトについて、チームの空き時間に
`Aチーム目標.パターン` に応じた段を 1 段ずつ自動で回します。
- `SPDCA`: `S`（相談）→ `P`（計画）→ `D`（実行）→ `C`（評価）→ `A`（改善）の5段。`A` の次は `S` へ戻る
- `PlanDo`（既定）: `P`（計画）→ `D`（実行）の2段。`D` の次は `P` へ戻る

その実行状況を「1レコード＝1作業」で記録するテーブルです。
`S` は計画を立てる前の意見交換で、n 名が並行してそれぞれの意見を出し、次の `P` でそれらを 1 つの計画にまとめます。

| 項目 | 内容 |
|------|------|
| `改善ID` | 主キー。`C採番`（採番ID=`Aチーム改善`、初期値1000）による`TP`＋8桁連番 |
| `プロジェクト` | 対象プロジェクトのパス（`Aチーム目標` の `CODE_BASE_PATH`） |
| `ループ` | PDCAサイクル番号。S投入時にそのプロジェクトの最大値+1を採番し、同じ段の複数要員と後続Pで共有する |
| `作業ID` | 投入した `Aチーム作業` の作業ID |
| `チーム目標` | 投入時点のチーム目標（後から目標を変えても記録は残す） |
| `要員ID` | 実行する要員 |
| `PDCA区分` | `S`=相談 / `P`=計画 / `D`=実行 / `C`=評価 / `A`=改善。パターンごとの並びで回り続ける（`パターン区分一覧`参照） |
| `状況` | 対応する `Aチーム作業` の状態を写した表示用の値（`準備中` → `準備完了` → `実行中` → `完了` / `エラー` / `中止`） |
| `開始日時` | 投入日時 |
| `終了日時` | 空ならその段はまだ実行中。次段へ進めるかどうかはこの終了日時だけで判断する（`状況`は表示用のため判定に使わない） |
| `応答内容` | AIタスクの応答（backend_task が反映） |
| `まとめ内容` | 経験生成後の内容。Sの成功結果をPの計画材料として使用 |
| 監査8項目 | 登録・更新の日時、利用者ID、利用者名、端末ID |

投入の条件（`team_watcher.py` の毎分確認）は次のすべてです。

- 前回の投入プロセス（`team_sub/sub_SPDCA_*.py` / `team_sub/sub_PlanDo_*.py`）が残っていない
- `Aチーム状況` に `実行数 > 0` の要員が 1 人もいない（＝チームの空き時間）
- 対象プロジェクトの `Aチーム改善` に未終了（`終了日時` が空）のレコードが無い
- 次の区分がそのパターンの区分一覧の先頭（新サイクルの開始）の場合、`Aチーム改善.ループ`の最大値が
  目標の最大ループ回数未満（`99`なら回数制限なし）
- 次の区分がそのパターンで実装済み（未実装の区分が次になったサイクルは何も投入しない）

区分の決め方は「レコードなし → パターンの先頭区分」「直前の段が終了 → その次の区分（末尾の次は先頭へ戻る）」です。
1回のサイクルで投入するのは 1 プロジェクト分だけです。

`S`（`team_sub/sub_SPDCA_soudan.py`）は admin 以外の有効な要員から `Aチーム目標.動員要員数`（既定 2）名を
ランダムに選び（動員要員数が admin 以外の有効要員数を超える場合はその全員、1 名もいなければ admin）、要員ごとに `Aチーム作業`（状態=`準備中`）→ `Aチーム改善` の
開始レコード → `aidiy_task_agents` への投入（`Aタスク要求`）を作ります。各要員には「結論を 1 つに決めず、
目標に効く取り組みを 1〜3 件挙げる」意見出しを依頼します（調査のみで変更は禁止）。
投入前に最大ループ番号を再確認し、上限未到達なら最大値+1を今回の番号として全Sレコードへ書き込みます。
担当は決まっているため `sub_init.py` の AI による担当選択は通しません。
投入に失敗した作業はエラーにし、対応する改善レコードも終了させます。

`P`（`team_sub/sub_SPDCA_plan.py`）は、`Aチーム改善.ループ`の最大値に一致するSが全件`済`または`エラー`に
なった後に1件だけ投入します。そのループのSだけを直接取得し、`済`レコードにあるまとめ内容をすべて計画材料にして、
成功レコードを作った要員から担当をランダムに1名選び、
後続Dが着手できる具体的な実行計画へ取りまとめます。全Sがエラーの場合はS参加者から担当を選び、目標と現状を基に
計画を作成します。`済`のSが1件だけならAIを起動せず、要員・目標・応答・まとめ内容を引き継いだ同一ループの
`P / 済`レコードをupsertして次段へ進めます。それ以外はP用のAチーム作業IDを採番して開始日時を記録し、
Sと同様に新しい`Aタスク要求`として直接投入します。どちらもPの改善レコードは直前Sのループ番号を引き継ぎます。

共通処理は `team_sub/sub_SPDCA__common.py` にまとめ、全 5 段がここを通ります。

- 前段の全レコードが`済`または`エラー`であることの確認（`前段結果を取得`）
- 前段から次段へ引き渡す本文の取り出し（`最新の成功記録` / `まとめ内容`。まとめ内容が空なら応答内容）
- `Aチーム作業`（状態=`準備中`）→ `Aチーム改善` の開始レコード → `aidiy_task_agents` への投入（`段を投入`）
- 引き継ぐ内容が無いときに終了済みレコードだけ残して次段へ送る処理（`実行不能を記録`）

`D`・`C`・`A` はさらに「直前の段のまとめ内容（最新1件）を受け取り、1件だけ投入する」という
流れまで同じなので、メイン処理ごと共通処理（`段を実行`）が引き受けます。各スクリプトはプロンプトだけを定義します。
担当の決め方は段ごとに異なり、`段を実行`の`要員継続`引数で切り替えます。

- `D`（`要員継続=True`）: 新たにAIへ選ばせず、`P`の担当要員をそのまま引き継ぐ
- `C`（`要員継続=False`、既定）: `sub_init.py`と同じAI選択（有効な要員一覧 + `Aチーム経験`の
  経験値・直近の学びを渡し、選択結果を`temp/output/pdca_<区分>_<ループ>.json`で受け取る。失敗時は`admin`）
- `A`（`要員継続=True`）: 新たにAIへ選ばせず、`C`の担当要員をそのまま引き継ぐ

`S` と `P` はメイン処理の流れが違うため、それぞれの実装に残しています。

| | 前段の取り方 | 担当の決め方 | 投入件数 |
|---|---|---|---|
| `S` | 前ループの`A`（同ループに前段なし）。ループ番号を新規採番 | admin以外を候補にAI選択（動員要員数まで、重複なく順に選抜） | 動員要員数ぶん |
| `P` | 同ループの`S`の成功レコード全件 | `S`成功者からランダム | 1件（成功Sが1件ならAIを起動せずupsert） |
| `D` | 同ループの`P`の最新1件 | `P`の担当を継続 | 1件 |
| `C` | 同ループの`D`の最新1件 | AI選択（経験ベース） | 1件 |
| `A` | 同ループの`C`の最新1件 | `C`の担当を継続 | 1件 |

前段が全件エラー、または引き継ぐ内容が空の場合は、終了済みレコードだけを残して次の段へ進めます
（未投入のままだと毎分その段の投入が再試行され、改善ループが止まるため）。

| 区分 | スクリプト | 前段 | AIへの依頼内容 | 変更の可否 |
|------|-----------|------|----------------|-----------|
| `D` | `team_sub/sub_SPDCA_do.py` | `P` | 計画のステップを実施し、変更内容と動作確認結果を報告する | ソース変更可（この段だけ） |
| `C` | `team_sub/sub_SPDCA_check.py` | `D` | 実施報告を実物に当たって検査し、判定・根拠・問題点を報告する | 不可（読み取りとテスト実行のみ） |
| `A` | `team_sub/sub_SPDCA_action.py` | `C` | 実際に動作させて改善点を洗い出し、優先度付きで報告する | 不可（動作確認の実行はしてよい） |

`D` は計画外への拡大、git のコミット・プッシュ、破壊的操作を禁止と指示します。
`A` のまとめ内容は次サイクルの `S`（相談）へ引き継がれ、そこから改善が続きます。

`S` は2周目以降、1つ前のループの`A`（`済`のうち最新1件）のまとめ内容をプロンプトに含め、
「ゼロから考え直さず、前サイクルで残った改善点のうち取り組む価値が高いものを見極める」よう指示します。
初回（ループ1）や前サイクルのAが`済`でない場合は引き継ぎなしで従来どおり動きます。

区分を実装するときは、`team_sub/sub_SPDCA_<区分名>.py`（または `sub_PlanDo_<区分名>.py`）を追加し、
`team_pdca_db.パターン区分一覧` と `team_watcher._SUB_PDCAパス` の該当パターンに 1 行足します。

`Aチーム作業` が終わっているのに改善レコードが未終了のまま残った場合は、毎分の確認と起動時
クリーンアップで回収し（`状況` にはそのときの作業の状態を写す）、次の段へ進めるようにします。
回収は改善ループのオン・オフに関わらず毎分行います（起動時は `起動時改善ループをオフ` で必ず
オフになるため、オンのプロジェクトだけを対象にすると起動直後に確定した作業を回収できないため）。
回収するのは次のどちらかです。

- `Aチーム作業` が `済` / `エラー` / `中止`
- `Aチーム作業` が `完了`（経験生成待ち）のまま滞留している。経験生成が失敗すると
  `Aチーム経験` だけがエラーになり、作業は `完了`・改善は未終了のまま誰も閉じず、経験の
  再生成も走らない（`経験対象一覧` は経験レコードが無いものだけを拾う）ため、
  対応する経験が `エラー` で確定したもの、または `完了滞留回収分`（90分）を過ぎても
  `済` にならないものを回収する

フロントエンド（`/AIチーム` 画面の改善一覧）は、掲示板に出ている目標の `改善ループ` がオンのときだけ
パネルを表示し（オフなら描画しない）、そのプロジェクトの記録を「何を（PDCA区分）／誰が（要員ID）／開始日時」で
一覧します。行のダブルクリックでチーム目標・応答内容を共通の要求応答ダイアログに出します。

## Aチーム状況

要員ごとにAタスク要求の状況を集計した読取専用テーブルです。書き込みはbackend_task側
（実行開始条件の監視ループ、10秒間隔の最後）が行い、集計のたびにテーブル全体を作り直します。
対象は「有効なAチーム要員」×「実行有効なAタスク要求（利用者ID＝要員ID、更新日時が24時間以内）」です。

| 項目 | 内容 |
|------|------|
| `要員ID` | 主キー |
| `要員名` | 表示名（集計時点のAチーム要員から複写） |
| `最終更新日時` | 対象Aタスク要求の更新日時の最大値 |
| `待機数` | 状態が `準備完了` / `待機` の件数 |
| `実行数` | 状態が `準備中` / `実行中` の件数 |
| `まとめ中数` | `Aチーム経験`の開始日時が入り、終了日時が空の件数 |
| `経験最終更新日時` | 要員ごとの`Aチーム経験.更新日時`の最大値。待機時の雑談・休憩切替に使用 |
| `完了数` | 状態が `完了` の件数 |
| `エラー数` | 状態が `エラー` の件数 |

`Aチーム状況`に該当要員の行が無い場合、エージェント状態は推測で変更せず現在値を維持する。実行・まとめがないときは、`経験最終更新日時`または要員IDで絞った`Aタスク要求`の`最終更新日時`の新しい方が1分以内なら無条件で休憩中とする。要員状況画面は5秒間隔で最大更新日時を確認し、変化時だけ一覧を再取得する。
| `更新日時` | この集計行が作られた日時 |

有効なAチーム要員は、対象のAタスク要求がなくても各件数0の行を作成します。

| `team_proc/team_goal_db.py` | `Aチーム目標` の作成、初期投入、参照、upsert、削除 |
| `team_proc/team_exp_db.py` | `Aチーム経験` の作成、対象抽出、仮登録、本登録、失敗記録、タイムアウト |
| `team_proc/team_pdca_db.py` | `Aチーム改善` の作成、次のPDCA区分の判定、開始レコード登録、取り残し回収、クリア |
| `team_proc/team_status_db.py` | `Aチーム状況` の読取専用アクセス（更新はbackend_task側）と実行中要員数の判定 |
| `team_proc/team_watcher.py` | 5秒間隔で準備開始の作業を取得し、準備中へ更新して`team_sub/sub_init.py`を起動。1分ごとに無進捗タイムアウト確認・`Aチーム経験`の生成・`Aチーム改善`の回収・改善ループの確認を行う |
| `team_sub/sub_init.py` | 担当要員をAIに選ばせ（`Aチーム経験`の経験値・学びも判断材料に渡す）、作業IDを`task_id`に指定して`aidiy_task_agents`へ投入し、同じIDをAタスク要求へ引き継ぐ。成功時にAチーム作業を準備完了へ更新 |
| `team_sub/sub_exp.py` | AIタスク明細から経験値をまとめさせ（2段構え、`backend_task/task_sub/sub_init.py`と同じ流れ）、`Aチーム経験`へ本登録 |
| `team_sub/sub_SPDCA_soudan.py` | 改善ループの `S`（相談）。admin以外を候補に`Aチーム目標.動員要員数`まで（有効要員数が上限）AIへ順に選ばせ、計画前の意見出しをさせる作業を`Aチーム改善`・`Aチーム作業`・`Aタスク要求`に作る |
| `team_sub/sub_SPDCA_plan.py` | 改善ループの `P`（計画）。完了したSのまとめ内容を成功したS担当者の誰か1名へ渡し、1つの計画として新規タスク投入する |
| `team_sub/sub_SPDCA__common.py` | 改善ループ全区分の共通処理（前段確認、まとめ内容の受け渡し、作業/改善レコード作成、タスク投入）。`D`・`C`・`A` はメイン処理もここが引き受け、`段を実行`の`要員継続`引数でAI選択（`C`）と前段担当の引き継ぎ（`D`・`A`）を切り替える。各スクリプトはプロンプトだけを持つ |
| `team_sub/sub_SPDCA_do.py` | 改善ループの `D`（実行）。完了したPの計画をPの担当要員がそのまま実施する。変更を許可する唯一の段 |
| `team_sub/sub_SPDCA_check.py` | 改善ループの `C`（評価）。完了したDの実施報告を、経験ベースでAIが新たに選んだ要員が実物に当たって検査させる（変更禁止） |
| `team_sub/sub_SPDCA_action.py` | 改善ループの `A`（改善）。完了したCの検査結果をもとにCの担当要員がそのまま実際に動作させ、改善点を洗い出す（変更禁止）。結果は次サイクルのSへ引き継ぐ |
| `team_proc/runtime.py` | lifespan、再起動監視 |
| `_start.py` / `_setup.py` / `_cleanup.py` | 全体スクリプトからの委譲先 |
| `persona/<要員ID>/persona.json` | 召喚候補。フォルダ名は1～16文字、空白なしで、英数字・日本語・`_`・`-`のみ。`admin` は削除禁止初期要員 |
| `team_proc/persona_catalog.py` | personaフォルダの検証、読込、召喚要員一覧化 |
