# 説明資料の書き方

> 文書: `セルフテスト,_説明資料の書き方.md` | 実装: `_AIDIY/knowledge/_index.md`, `scripts/checks/実画面試験記録.mjs`

## 必須ルール：最新版だけ・内容が分かる名前

- 資料・画像・PDFは常に最新版だけを維持します。旧版、修正前、途中経過、比較用の退避コピーは残しません。
- ファイル名は短い編名・確認番号・内容に揃えます。日付、変更後、修正後、追加後、確認02、確認03、最新版、旧版などの作業経緯を付けません。
- 例：`Diag-アプリ起動_103_アイコン収納.png`、`生産在庫_505_在庫更新.jpg`。日時・実施条件・結果は本文に書きます。
- 同じ場面は同名で置き換えます。異なる条件を併記する場合だけ、条件が分かる内容名で区別します。
- 更新時は本文の参照リンクとPDFを一緒に更新します。参照のなくなった旧画像・旧台帳・ログは整理し、リンク切れがないことを確認します。
- 試験終了時は正式資料だけでなく、`temp/`・`tmp/`・`.aidiy_cache/selftest/`・プロジェクト直下に残った撮影画像、比較画像、PDFのページ画像・コンタクトシートも整理します。採用する画像は正式資料へ配置して参照とPDFを確認し、採用元の一時コピーは削除します。アプリ用画像・依存キャッシュ・試験コードは区別して維持します。
- 未実施・未確認の範囲は本文に残します。資料の整理を再試験の成功として扱いません。

## このメモを使う場面

- 総合テストの手順・結果をまとめるとき。
- 確認画像を添え、操作手順書の素材として残すとき。
- 説明の分かりやすさ・簡潔さ・丁寧さを見直すとき。

## 基本の書き方

- 解消済みの失敗・再試行の経緯は掲載せず、判定は最終結果だけを記載します。使用プロバイダ、手動の音声オン、待ち時間などの再現条件は注意書きにまとめます。意図的な異常条件の試験は、その条件と期待する動作を明記し、試験結果の失敗と混同しないようにします。

文書全体を、初めて使う方が操作を追える説明にします。

- 結論を先に、説明は短く具体的に書きます。
- 「です・ます」を基本に、対等で丁寧な言い方にします。
- 命令調や、読み手を責める表現は避けます。
- 同じ説明を繰り返さず、専門用語は初出で短く説明します。
- 操作する場所、ボタン名、待ち時間、成功の目印は残します。
- 読む人の知識や経験を見出し・本文で分類せず、説明自体を分かりやすく整えます。
- 前提知識を求めず、画面に出る名前と実際の操作に沿って説明します。読者層を示す対象者ラベルは資料に書きません。
- 内部データ、ログ本文、ハッシュ、細かな測定値を並べません。操作に必要な値と、確認した結果だけを残します。
- 確認用のJSON・ログ・結果テキストや、整理作業の台帳を説明資料として残しません。必要な確認を終えたら、その事実と判定だけを本文に記載します。

| 回りくどい・強い表現 | 書き換え例 |
|---|---|
| フォルダ選択の操作を行っていただく必要があります。 | 「フォルダ選択」を押します。 |
| ちゃんと接続を確認してください。 | 上部に「接続済み」と出れば、接続確認は完了です。 |
| しばらく待ちます。 | 準備完了後、初回は15秒程度待ちます。 |

待ち時間は、実装や試験条件を確認して書きます。上の15秒はLiveの例です。

## 文書の構成

| 順番 | 書くこと |
|---|---|
| 先頭：総合評価 | 評価日・対象環境、確認済みの範囲、未確認の項目、全体の合否、PDFの発行状況 |
| 始める前に | 必要な準備と、前に読む冊子へのリンク |
| 各章：操作手順 | 利用する順に、押す場所と操作を短く記載 |
| 成功の見分け方 | 完了表示、画面の変化、返答などの確認ポイント |
| 今回の結果と画面 | 実際の結果、判定、短い説明を添えた画像 |
| 必要な補足 | 操作上の注意、確認していない範囲、操作に必要な注意書きを短く記載 |

主目的は総合テストの実施記録です。操作手順書の素材は、その副産物として残します。起動・アプリ操作・環境確認は別冊に分け、共通手順はリンクで案内します。

## 画像の添え方

**説明なしで画像を並べません。各画像の直前に、場面と確認ポイントを1〜2文で添えます。**

画像名は `短い編名_確認番号_場面.png` に統一します。画像はセルフテストの冊子ごとのフォルダにまとめ、`配車管理_103_日時逆転拒否.jpg`、`生産在庫_504_在庫推移.jpg`、`Task_202_即時実行完了.jpg`、`Team_504_自動会話.png` のように短い編名を使います。廃止機能の旧資料・画像は、現行資料や実装から参照されていないことを確認して削除します。過去の復元はGit履歴を使い、現行ナレッジに退避コピーを残しません。日付・時刻・実施IDはファイル名の先頭へ付けず、実施日時は本文へ記載します。同じ場面を撮り直すときは最新画像に置き換え、本文・PDFも同時に更新します。参照がなくなった旧画像は削除し、版違いのコピーを残しません。試験データの識別用実施IDは、下記の従来ルールを維持します。

画像名・参照パスだけを整理し、表示本文・画像内容・判定を変えない場合は、既存PDFの表示内容は変わりません。PDFに旧ファイル名が本文として表示されていないことを確認したうえで、そのPDFは維持できます。表示本文・画像・判定を変更した場合は従来どおりPDFも再生成します。

「古い履歴を不要とする」は、作業経緯・重複した試行・修正前の結果を整理する意味です。現行の操作説明に使える画面まで除外しません。開始、対象選択、閲覧、検索、AIへの依頼、表示切替、終了を画像と文章でたどれることを確認します。画像の採否は撮影日の新旧だけで決めず、現行の操作・ボタン名・結果との一致で判断します。一致しない画像は現行画面へ差し替えます。

セルフテストの表だけで操作説明を代用しません。「どこを押す → 何が表示される → どこで成功を見分ける」を各章へ記載し、その説明の近くに画面を配置します。実機・Web・隔離試験の違いは短く明記し、資料の編集だけを実機再試験として記録しません。

説明例：

> フォルダ選択後の画面です。選んだパスが表示され、起動ボタンが有効になりました。

この説明の直後に、対応する実画面を1枚掲載します。画像名や代替テキストだけに説明を任せません。判定を確認できる最終状態の画像を使います。

## 試験の準備と終了

起動は[システム起動編](./セルフテスト,aidiy_diag,システム起動編.md)、作業フォルダの選択・アプリ起動・この開発PCの試験用アカウントは[アプリ起動編](./セルフテスト,aidiy_diag,アプリ起動編.md)を参照します。Web・Avatarの試験ではLocal以外の5機能を起動し、Diagをミニ表示にして、試験中は閉じません。Avatar Webは、先にAvatarを起動して8092を待受状態にします。

通常のログイン操作を確認し、認証情報・JWTを画像やログへ露出させません。実施範囲と結果は各編へ記載します。表の1行に複数対象がある場合は、ケースIDに対象ごとの枝番を付け、一つの成功で行全体を合格にしません。

利用者指定のこの開発PCのセルフテスト用アカウントは、利用者ID `admin`、パスワード `********`（伏字ではなくアスタリスク8文字）です。DiagのCoreログイン、Task／Team等の試験に使います。別環境へ流用せず、入力済みの認証欄やJWTは証跡へ掲載しません。

### 試験データ

1. 実施IDを `YYYYMMDD-HHMMSS-web-avatar` とします。同じ試験に含まれる冊子と証跡で共用します。冊数は固定しません。
2. `temp/総合テスト/<実施ID>/project/` を作り、AIへ渡す作業フォルダに指定します。実装ソースをAIの変更先にしません。
3. そこへ `挨拶.txt`（内容：`おはよう。総合テスト用です。`）、`日本語 フォルダ/確認.txt`、小さなPNG画像を用意します。保存後に元のファイルと照合し、本文には一致したかどうかだけを記載します。
4. DB登録の名称には `SELFTEST-<実施ID>-` を付けます。実際に払い出されたID・元の値・参照関係・片づけの結果を、各編の試験データ表へ記録します。項目の長さ・型に合わせ、主キーへ長い接頭辞を無理に入れません。
5. モデル・表示・目標・自動実行など、変更する設定の元値を記録します。キー本体とJWTは保存しません。共有DB全体の復元や既存レコードの削除は行いません。

### 終了時

試験で作った定期実行・チーム自動作業を先に停止し、実行中の試験タスクがないことを確認します。元の設定を戻し、試験データだけを参照先から順に片づけます。記録・画像・生成物の証跡は残します。既存のadmin要員や利用者・既存業務データは削除しません。

Diagを閉じると管理中のシステムが止まるため、Web／Avatar試験の途中では閉じません。Diagから起動したAvatar等のアプリは独立実行です。最終停止ではアプリも個別に閉じ、残った子プロセスとポートを確認します。`python`、`node`、`electron`の名前だけによる全停止は避け、起点・引数・親子関係からAiDiyの対象を特定します。

## 操作と待ち時間

Computer Useで実画面を操作します。API・ログ・DBは結果の裏付けに使えますが、APIだけで画面操作を済ませたことにはしません。実施方式を結果に添えます。

| 場面 | 試験の待ち方 |
|---|---|
| 通常の画面・保存 | 最大30秒を目安に表示・完了を確認します。超えたら通信とログを調べ、時間を記録します。 |
| Chat／Codeの短い質問 | 送信後は最大120秒を初期観測枠にします。進捗があれば最大300秒まで観測し、延長理由を残します。アプリのタイムアウト設定とは別です。 |
| Liveの初回／再接続後 | 接続済み・準備完了を確認して15秒待ち、送信後は最大60秒待ちます。初回送信で返答があるか、この条件で確認します。 |
| 画像生成 | 最大300秒を初期観測枠とし、実装の制限と進捗を確認します。受付表示だけで生成成功にしません。 |
| チームのプロジェクト会話 | 最大360秒。プロジェクト調査を伴うため、即応を前提にしません。 |
| AIタスク | 5秒の起動監視・10秒の状態監視を考慮します。開始条件の判定は毎分です。分解の既定上限30分、無進捗の要求60分、明細は見積りの2倍・最低10分です。短い要求でも進捗を見て判断します。 |

Liveで15秒待機して送信した場合は、報告に `※注意:15s待機後送信しました。` と事実を記載します。準備完了からの待機と送信後の応答待ちを分け、初回送信か再送かも明記します。接続成立からの時間を測っていない場合は、その点も残します。

標準は準備完了後15秒待機・送信後最大60秒観測です。15秒はプロバイダの応答を保証する時間ではありません。20秒・30秒待機は個別に指定された追加比較として扱い、標準試験で自動的に延長しません。追加比較を行った場合は実際に待った時間を記載し、新規接続の初回送信と同一接続での再送を分けます。プロバイダの状況も変わるため、各1回の結果だけで待機時間との因果関係や製品不具合を断定しません。

長い待機中も30～60秒程度ごとに進捗を確認し、利用者へ状況を伝えます。試験の観測時間切れと、製品が返したエラーを区別します。完了前に止めたケースは未実施部分を残し、成功扱いにしません。

入力文・対象プロバイダ／モデル・確認範囲は各編の試験項目に従います。「おはよう」への簡易応答確認と、ファイル読取・作成やプロバイダ比較の試験を混同しません。利用上限だけを理由に別モデルへ変更した場合は、元の対象の結果も残します。

LiveのFreeAIで失敗・応答未確認となった場合は、利用枠制限の可能性も考慮し、同じ処理を共用するGeminiへ画面のモデル選択で切り替えて試験します。準備完了後15秒待機・送信後最大60秒の標準条件で実回答を確認できれば、共通Live機能の試験は通過とします。切替前後のプロバイダ・モデル、待機条件、実際の結果を記載します。FreeAI個別の失敗・未確認は参考結果として残し、Geminiでの成功をFreeAI自体の成功とは記載しません。利用枠制限も、裏付けがなければ原因の候補にとどめます。

## 結果の伝え方

| 表記 | 意味 |
|---|---|
| ✅ OK | 記載した条件で、良好な結果を確認できました。 |
| PASS（環境依存・判定対象外） | Mac／Linux実機、長時間連続運転、機器・権限・任意サービスの不足などで今回の判定から除外する項目です。理由と未実施範囲を添え、実行成功や製品不具合とは区別します。 |
| ❌ NG | 環境がそろった状態で試し、期待する結果が得られませんでした。 |
| ⏸ 未実施 | まだ試していません。不具合とは分けて扱います。 |
| ⏸ 未確認 | 試行したものの、成功・失敗を確定できる証拠が不足しています。 |
| ⏸ 未測定 | 時間や寸法などを、まだ測っていません。 |

総合評価は `✅ OK（記載した確認範囲）` を基本とし、試験日・環境・確認方法を添えます。環境依存の除外は `PASS（環境依存・判定対象外）` に統一し、理由と未実施範囲を列挙します。件数を示す場合はケース・条件・自動試験のどれを数えたか明記し、重複して数えません。後続の別冊や任意の未試験機能は「対象外」、試したが判断材料が不足する場合は「⏸ 未確認」とします。未実施・未確認を一律にPASSへ置き換えません。代替プロバイダで確認できた共通処理は `✅ OK（代替確認）` とし、元プロバイダの成功とは区別します。

起動要求の受付、画面の表示、AIの返答は、それぞれ確認します。文字の返答と音声の再生・聴取も分けて記録します。

資料には修正後の最終結果だけを掲載します。**解消した課題の経緯は記載不要です。**修正前の失敗、旧設定での試行、途中経過、取り直し前の画像は本文や折りたたみ欄へ残しません。現在も必要な試験条件・未実施項目・制約は明記します。再試験後は結果と総合評価を更新し、未確認の項目を文面だけで合格に変えません。

### 本文に残す結果とAI応答の判定

空応答、`!`だけ、`!`から始まる回答はエラーです。エラー表示が正しく出ることと、AIの正常応答を別に判定します。エラー表示試験には隔離したモックを使えますが、実プロバイダの成功試験を置き換えません。

結果は各編の本文と表へ直接記載し、操作・成功の目印・確認結果・未確認事項が分かるようにします。JSONやログで裏付けを確認した場合も、内容の転載や数値の羅列は不要です。「保存データとログでも照合し、一致を確認しました」のように、確認した事実と判定を短く残します。実際に確認していないものまで確認済みと書きません。

| 記録すること | 本文への書き方 |
|---|---|
| 実施条件 | 実施日時、対象OS、操作方式、機能・プロバイダ・モデルを記載します。 |
| 結果 | 返答が出た、保存内容が一致した、処理が完了したなど、確認できたことを短く書きます。 |
| 待ち時間など | 操作に必要な待ち時間は残します。内部の処理時間・画面座標・細かな測定値は並べません。 |
| 未確認・環境不足 | 試せなかった項目と理由を、成功した項目と分けて記載します。 |
| 再試験 | 対象ケースの条件・判定・画像を、修正後の最終結果へ置き換えます。旧試行との比較は掲載しません。 |

画像は説明付きで本文に掲載します。自動生成された詳細記録を説明資料のフォルダへコピーしたり、JSON・ログ・結果テキストへのリンクや文字表示を追加したりしません。確認した事実だけで説明が足りる場合、別の表や資料を追加しません。

## ファイル・画像・PDF

テスト文書名は `セルフテスト,アプリコマンド,xx編.md` とします。

画像の保存先は `_AIDIY/knowledge/images/<参照元Markdownの拡張子なしファイル名>/` です。実施日時・結果・操作上の注意・画像説明は参照元のMarkdownへ直接記載します。JSON・ログ・結果テキストや、実施IDなどのサブフォルダは作りません。新しい画像名は短い編名・確認番号・場面の順にし、日付や実施IDは先頭に付けません。

| 冊子 | フォルダ名（参照元.mdの拡張子なし） | 画像名の例 |
|---|---|---|
| Web AiDiy | `セルフテスト,frontend_web,AiDiy編` | `AiDiy_101_ログイン後画面.png` |
| Task | `セルフテスト,aidiy_task,操作編` | `Task_101_要求一覧.png` |
| Team | `セルフテスト,aidiy_team,操作編` | `Team_101_要員召喚.png` |
| Web 配車管理 | `セルフテスト,frontend_web,配車管理編` | `配車管理_101_一覧画面.png` |
| Web 生産・在庫管理 | `セルフテスト,frontend_web,生産・在庫管理編` | `生産在庫_101_一覧画面.png` |
| Avatar Electron | `セルフテスト,aidiy_avatar,Electron実行編` | `Avatar-Electron_101_ログイン後画面.png` |
| Avatar Web | `セルフテスト,aidiy_avatar,Web実行編` | `Avatar-Web_101_ログイン後画面.png` |

確認番号は元の試験ケースや撮影場面と照合するための番号です。新規採番は章番号と章内連番を基本にしますが、分冊・章移動では既存番号を維持します。同じケースの再試験は本文・画像・PDFを最新版へ置き換えます。比較用の旧版は残さず、参照されなくなった旧画像を削除します。実画面PNGを保存し、対象の操作と確認結果を本文へ記載します。照合用のハッシュ文字列は載せず、照合した事実と結果だけを残します。動画や連続画像はズーム・ドラッグなど動きの証拠に使えます。静止画1枚だけで動作時間を確認したことにはしません。

画像名を整理するときは画像内容を変えず、本文の参照を同時に更新します。同じ場面の再撮影は同じ名前で最新版へ置き換えます。異なる試験条件の画像を両方残す必要がある場合は、「狭幅」「未接続」など内容の違いが分かる名前にします。版番号や撮影日は付けません。複数文書が共有する画像は、それぞれの文書フォルダにコピーします。本書は書き方のルールだけを扱い、試験結果や作業記録を保管する専用フォルダは作りません。画像は対応する各編へ整理し、確認した事実と判定は各編の本文に残します。

本文には画像の直前に「何を操作し、どこを確認できたか」を1～2文で書き、相対リンクでインライン掲載します。説明なしの画像一覧や、存在しない画像への予約リンクを作りません。ログイン画面のパスワードは伏せた状態で保存します。

### 画像の大きさをそろえる

掲載画像は縦横とも960px以下とし、縦横比を保ちます。横長の画像は横幅、縦長の画像は縦幅が上限に収まるよう縮小し、小さい画像は拡大しません。画像を追加した後、プロジェクトの起点で次を実行します。

```powershell
python _AIDIY/knowledge/images/画像サイズ調整.py
```

変更せず大きさだけを確認する場合は、末尾に `--check` を付けます。特定のフォルダだけを処理する場合は、そのパスを末尾に指定します。上限を変える場合は `--max-width 960 --max-height 960` の数値を指定します。Pillowが必要です。ファイル名と文書のリンクは変わりません。JSONやログなどの記録ファイルは作りません。

### PDFを作成する

撮影補助を使う場合、`scripts/checks/実画面試験記録.mjs` はDiag3冊とIDE、`scripts/checks/総合テスト補助/chrome操作.mjs` はWeb5冊とAvatar2冊に対応しています。補助処理の出力があっても、操作・結果・画像説明は各編の本文へ反映します。手動で記録する場合に、別の機械用ファイルを作る必要はありません。

1冊通過するごとに、起点で次を実行します。`対象.md` は実際の冊子名へ置き換えます。引数は `_AIDIY/knowledge/` からの相対名（ファイル名だけ）で、複数を並べられます。

```powershell
node scripts/checks/総合テストPDF.mjs 'セルフテスト,frontend_web,AiDiy編.md'
```

PDFは、元のMarkdownと同じフォルダに同じ名前で保存します。上の例では `_AIDIY/knowledge/セルフテスト,frontend_web,AiDiy編.md` の隣に `セルフテスト,frontend_web,AiDiy編.pdf` ができます。本文からは `[PDF版](./セルフテスト,frontend_web,AiDiy編.pdf)` のように相対リンクで案内します。`output/pdf/` へは保存しません。

本文を修正したらPDFも再生成し、日本語、表、全画像、折りたたみ部分、改ページの見切れを確認します。PDFの生成成功と目視確認を分けて記録します。未実施の計画に合格済みPDFは付けません。PDFを画像にする道具がない環境では、`aidiy_chrome_devtools` でPDFを新しいタブに開き、ホイール操作でページを送って撮影すると確認できます。

対象外の機能やOSは先に明記します。Windows試験では、Mac／Linux実機と長時間連続運転は「PASS（環境依存・判定対象外）」とし、未実施であることを明記します。

## 透過ウィンドウを映り込みなく撮影する

アイコン表示は背景が透過するため、背後に白い専用ウィンドウを表示してから実画面を撮影します。デスクトップの壁紙・アイコン・他アプリを写し込まず、撮影後の画像加工で隠す方法は使いません。

1. 対象の表示モード・ピン設定を控えます。撮影の邪魔になるIDEなどは、利用者の意図と未保存作業を確認して閉じます。
2. プロジェクトルートのPowerShellから、次を実行して白背景を表示します。このウィンドウは撮影用なので意図的に表示します。

   ```powershell
   Start-Process -FilePath (Resolve-Path 'backend_diag/node_modules/electron/dist/electron.exe').Path -ArgumentList ('"' + (Resolve-Path 'scripts/checks/撮影用白背景.cjs').Path + '"') -WindowStyle Normal
   ```

3. Diagを白背景より前面に置きます。アイコン表示は最前面を維持します。通常／ランチャー表示では必要に応じてピンをONにします。
4. 通常表示・ランチャー表示・アイコン展開・1個収納をそれぞれ撮影します。デザイン調整後は1個収納も撮り直します。モード変更後は窓サイズが落ち着くまで待ち、対象ウィンドウの最新の表示領域だけを取得します。
5. 白背景の空白部分をクリックしてポインターを対象外へ移し、ツールチップが消えてから保存します。実際の影や光は残します。
6. 画像は短い編名・確認番号・場面が分かる名前で保存し、同じ場面は最新画像に置き換えます。縦横960px以下に縮小し、小さいアイコン画像は拡大しません。本文の説明と参照を更新してPDFも再生成します。新規撮影後は最新画像へ参照を揃えます。参照更新後、廃止機能・重複・旧表示だけの不要画像は他の資料や実装から参照されていないことを確認して削除します。
7. 撮影用白背景をAlt+F4またはEscで閉じ、変更した表示モード・ピン設定を戻します。CLaunchなどを一時終了した場合だけ再起動します。他の常駐アプリを一律に終了しません。

## 仕上げの確認

ファイル名は短い編名・確認番号・内容だけにします。日付（例：20261028）、変更後・修正後・追加後、確認02・確認03、最新版・旧版など、作業経緯や版を示す語は禁止です。試験の日時・条件は本文へ書き、再試験でも同じ内容名を使います。

- 利用順に読み、押す場所と次の動きが分かりますか。
- 長い説明や同じ説明を、短くまとめられますか。
- データやログの内容を並べず、確認した事実と結果だけで伝わりますか。
- 読者の知識や経験を示す対象者ラベルが、見出しや本文に混ざっていませんか。
- 丁寧で、押しつけにならない言い方ですか。
- 各画像に短い説明があり、本文と画面が対応していますか。
- 総合評価と各章の結果は一致していますか。
- 画像・リンクが開き、保存した証拠が残っていますか。

構成例は[システム起動編](./セルフテスト,aidiy_diag,システム起動編.md)、各編への案内は[ナレッジ索引](./_index.md)、保存・更新の共通ルールは[ナレッジ更新手順](./共通,ナレッジ更新手順.md)を参照できます。

## 再テスト後も様式を維持する

各セルフテスト冊子のタイトル直後に、次の共通文を掲載します。

> 本書はセルフテスト結果を、操作説明・解説書としても読みやすく整理しています。再テスト後は結果・注意書き・エビデンスを更新し、章立て・操作手順・図解の配置などの様式を維持します。

結果が変わっても操作説明の章立て・図解・画像説明を維持します。新機能や利用者からの明示的な変更依頼がある場合にだけ、必要な範囲で構成を変えます。成功した機能、環境依存のPASS、主要メソッドの選定外を分けて記載します。SVGは説明図、実画面は証跡として区別し、両方を冊子単位のimagesフォルダへ保存します。

## 正式証跡と作業ファイルの分離

正式な画像・説明図・必要な音声だけを冊子別の `images` に置きます。撮影manifest・JSON・ログなどの作業結果は `.aidiy_cache/selftest/<冊子名>/` に保存し、Gitの対象外にします。日付・実施IDは作業領域の識別には使えますが、正式画像の名前の先頭には付けません。現行資料で参照する画像、音声、業務試験の証拠を日付だけで削除しません。Web／Avatar版Task／Teamの説明は残さず、単独Task／Teamの冊子へ案内します。
