# クリーンアップ手順

> 文書: `共通,クリーンアップ手順.md` | 実装: `_cleanup.py`, `_start.py`, `frontend_ide/host/_cleanup.py`, `scripts/checks/test_cleanup_residuals.py`

IDE群(Code / Live / IDE)はsetupと同様、全体cleanupで一括選択・一括処理する。`frontend_ide/_cleanup.py` が3種類の拡張・ランチャー・専用生成物と、共有通信基盤・共通UIの依存物をまとめて解除する。いずれかの停止・解除が失敗した場合は共有依存物を保持し、失敗として報告する。

実行ログの見出しと完了報告は「IDE群(Code / Live / IDE)」の1組に揃え、Code・Live・IDE・共通基盤を別々のクリーンアップ項目として表示しない。内部の担当関数は `report=False` で呼び、削除先・失敗理由の詳細は表示する。共有依存物は3種類の解除成功後に一度だけ削除する。表示名と停止要求のサービス識別子は分け、見出しの変更で監視側の停止対象を変えない。

## このメモを使う場面
- `_cleanup.py` の削除対象や確認プロンプトを変更する
- 一時ファイル、バックアップ、依存物の整理範囲を確認する
- cleanup 後に起動時再作成されるディレクトリを判断する

## 対象

- ルート `.aidiy_backup/`
- プロジェクト配下の全階層にある `temp/`、`_temp/`、`.temp/`、`tmp/`（隠しフォルダ内も含む。ただし `.aidiy_backup/` 内は除く）
- `backend_tools/aidiy_automations/temp/` など、サブプロジェクトの直下以外にある一時フォルダも対象
- `frontend_ide/host/node_modules/`、`frontend_ide/host/dist/`、`frontend_ide/host/aidiy_live/dist/`、`frontend_ide/host/out/`
- `frontend_channels/node_modules/`、`dist/`、`out/`、`temp/`、Python キャッシュ（共通設定・ソースは保持）
- `~/.local/bin` の単独起動ランチャー `aidiy_code` / `aidiy_live`（Windows は `.cmd`、旧名 `aidiy_vscode` を含む）
- 同じフォルダの `aidiy_diag` / `aidiy_ide` / `aidiy_console` / `aidiy_avatar` / `aidiy_hermes` / `aidiy_discord`（各選択項目の cleanup が担当）。Windows では共有フォルダが空になったときだけ、自動追加したユーザー PATH 登録も解除する。既存登録・他ツールが使用中の登録は保持する。登録記録と検証方法は `共通,開発環境運用手順.md` の「Windows のランチャーと PATH」を参照する。
- VS Code に配置済みで拡張名が `aidiy-` で始まる拡張機能（`publisher.aidiy-*`、Code / Live / 旧版を含む）
- 各 `.venv` / `venv`
- `node_modules`
- `dist`
- `__pycache__`

## 実装方針

- Diag の cleanup は、プロセス停止とランチャー解除に加え、`backend_diag/node_modules` と `backend_diag/ui/node_modules` を削除する。配布済みの `static/` は保持する。
- Tools の停止処理は、Python / MCP 接続だけでなく、この配置先の `backend_tools/temp/_chrome_profile` と `_chrome_profile_s数字` を `--user-data-dir` に指定した専用 Chrome も対象にする。通常の Chrome と別配置先のプロファイルは対象外。終了を確認できない場合は一時フォルダを削除しない。
- 全体 cleanup の最後に、全階層の `__pycache__` / `.pytest_cache` を削除する。`.aidiy_backup`、Git 管理情報、シンボリックリンク・ジャンクションの先には入らず、削除失敗は全体の失敗として返す。ソースとして同梱されたプラグインの `dist/` は一律削除しない。
- 何らかのクリーンアップを実行するときは、ファイル削除を始める前に全常駐サービスを各フォルダの `_start.py` が公開する `kill_ports()` で停止する（8090 / 8091 / 8092 / 8093 / 8095 / 8096、apps は 8098）。選択した削除対象だけに限定しない。
- Discord は待受ポートがないため、`frontend_channels/_start.py` の `kill_ports()` は `discord_processes.py` で実行入口を照合する。全体起動、npm start、aidiy_discord の Bot とその子孫を対象にし、他の Node.js や他の作業コピーを停止しない。終了確認失敗時は削除を中止する。全体 cleanup と Discord 単独 cleanup は停止要求ファイルで監視側の再起動を無効にする。
- IDE は空きポートで独立起動する。通常の全体起動・終了・リブートでは本体と子孫を継続し、cleanup 時だけ `frontend_ide/viewer/_start.py` の `kill_ports()` が実行入口を照合して停止する。Code / Live → IDE → Discord の順で停止・クリーンアップする。
- Code / Live の単独実行はランダムポートを使うため、上記のポート停止だけでは終了しない。ルートの削除前処理と `frontend_ide/host/_cleanup.py` は、この作業コピーの実行入口・Electron 実行ファイル・専用ブラウザプロファイルを完全一致で判定し、Windows では `taskkill /F /T` で強制終了する。終了を確認できない場合は削除を中止する。通常のブラウザと VS Code 本体は対象外。
- tools の `mcp_stdio.py` は MCP クライアント側の接続プロセスであり、8095 の待受プロセスを停止しても残る。ルートと tools 単独の cleanup は、この作業コピーの `.venv` / `venv` の Python、および `mcp_stdio.py` / `tools_main.py` の実行入口を照合して、接続プロセスと子孫も強制終了する。クライアント本体は終了しない。プロセス照合と終了確認は `scripts/_cleanup_processes.py` を共用する。
- tools の `.venv/Scripts/python.exe` で WinError 5、`temp/logs/*mcp_main.log` で WinError 32 が出た場合は、MCP 接続プロセスの残留を確認する。管理者権限の不足とは限らない。終了を確認できない場合は削除を中止し、ディレクトリの削除失敗は tools 単独・ルートともに失敗として終了する。削除対象の仮想環境から cleanup を実行すると自分自身が実行ファイルを保持するため、通常の Python で起動する。
- ルート `_start.py` が同時に稼働している場合は、`.cleanup_stop_request.json` で全常駐サービスを自動再起動対象から外す。要求ファイル自体は `_cleanup.py` の終了時に削除するが、監視プロセス内のサービス選択は無効のまま維持し、cleanup 後に勝手に再起動させない。
- Windows で停止要求元 PID の生存確認を行うときは `os.kill(pid, 0)` を使わない。Windows ではプロセス終了になるため、`OpenProcess` と `GetExitCodeProcess` で非破壊に確認する。
- ルート `_cleanup.py` は `find_temp_directories()` で `.aidiy_backup/` 内を除く全階層の `temp` / `_temp` / `.temp` / `tmp` と試験用の `test` / `_test` / `.test` を検索し、`cleanup_temp_directories()` でフォルダごと削除する。名前は大文字・小文字を区別せず完全一致で判定し、`templates` / `temp_data` / `tests` / `testdata` や同名の通常ファイルは対象にしない。`test` 系は依存パッケージの構成要素にもなるため、`node_modules` / `.venv` / `venv` / `site-packages` の配下では削除しない（temp 系は依存フォルダ内も削除する）。どちらも `.gitignore` で全階層を Git 管理外にしている。
- 一時フォルダはサブプロジェクトの選択に関係なく共通処理で削除する。個別の temp 削除質問はルートでは行わず、各フォルダの cleanup の後に全階層を整理する。`backend_local/temp` のダウンロード済みモデルも対象に含む。サブプロジェクト単独の cleanup は従来の選択方式を維持する。
- `.aidiy_backup` は共通の一時フォルダ検索・削除から全体を除外する。内部の `temp` / `_temp` / `.temp` / `tmp` / `test` / `_test` / `.test` も削除しない。専用の `cleanup_backup()` が削除確認後に本体を削除し、保持を選んだ場合は保存版の内容も保持する。旧 `backup/` は通常のフォルダとして扱い、一般の一時フォルダ削除規則を適用する。
- Git 管理情報（`.git`）とシンボリックリンク・ジャンクションの先は検索しない。対象の実体パスがプロジェクト内に収まることを削除直前にも確認する。親の一時フォルダを削除する場合、内部の同名フォルダは重複して列挙しない。
- 検索や削除に失敗した場合は全体の cleanup も失敗として終了する。
- `core_main.py` / `apps_main.py` / `tools_main.py` は起動時に必要な `temp` を再作成する。
- `command_hermes/temp` は CLI ツールの一時出力先なので cleanup 対象に含める。
- `frontend_ide/host` の cleanup は `aidiy-` で始まる拡張名を一覧から抽出し、`code --uninstall-extension` で解除する。対象が残っていないことを確認してから依存関係と生成物を削除し、解除を確認できない場合は削除を中止する。VS Code 本体は停止せず、解除の画面反映は利用者によるウィンドウ再読み込みに任せる。
- Code / Live はともに `extensionKind: ["workspace"]` とし、Linux へのリモート接続では同じ接続先へ配置する。Remote CLI の一覧・解除は接続先だけが対象で、旧版の Live を Windows 側へ配置していた場合は接続元で一度 `code --uninstall-extension aidiy.aidiy-live` を実行する。cleanup の案内でもこの対象範囲を明示する。
- ルート `.aidiy_backup/` は `_cleanup.py` の選択項目に含め、存在する場合は既定 `y` で削除確認する。
- `logs` は中身削除を維持する。ログフォルダ自体を削除する場合は、ログ設定側の再作成処理を先に確認する。
- `_cleanup.py` の仕様を変えたら、docs の code_samples に古い説明が残っていないか確認する。

## 検証方法

```powershell
python -m py_compile _cleanup.py _start.py frontend_ide/host/_cleanup.py
python -B -m unittest discover -s scripts/checks -p test_cleanup_residuals.py -v
python -B -m unittest discover -s scripts/checks -p test_diag_stop.py -v
```

停止処理は実サービスを起動せず、`_load_folder_start_module()` と `time.sleep()` をモックして、全サービスの `kill_ports()` が削除処理より先に呼ばれることを確認する。Windows では `_pid_is_running(os.getpid())` が `True` を返し、確認元プロセスが終了しないことも確認する。

一時フォルダの削除挙動は `scripts/checks/test_cleanup_residuals.py` で検証する。一時的なプロジェクト配下に3種類の名前、入れ子、似た名前の通常フォルダ、隠しフォルダ、リンクを作り、対象だけを削除し外部ファイルを保持することを確認する。サービス停止に失敗した場合の削除中止と、削除失敗の全体への伝播も確認する。

## 注意点

- 本番や共有環境で cleanup を実行する前に、削除対象の実体パスを確認する。
- ルート `.aidiy_backup/` は復旧材料になるため、削除確認プロンプトなしで消さない。
- 並列作業中は `_cleanup.py` と docs サンプルの担当者を確認し、担当外ファイルを編集しない。

旧 `.backup_local/` と `.aidiy_cache/` は一般の一時フォルダ・Pythonキャッシュ削除の巡回対象外とする。旧保存版は自動削除・移動しない。

## cleanup 後の残留確認

## 判断の基準

現時点の実装を正として、今後の開発・運用・検証に必要なものだけを残します。古い日付だけで削除せず、実装との一致、参照元、再利用の必要性を確認します。廃止機能の資料、修正前の結果、途中経過、重複コピーを現行資料に混在させません。

DB・設定・利用者データ・バックアップは残骸ではありません。明示的な削除指定がなければ保持します。`.aidiy_backup/` などの保存版は通常の残骸調査・編集対象に含めません。

## 1. cleanupの完了を確認する

1. プロジェクト直下の `_cleanup.py` を実行します。選択内容と終了結果を確認します。
2. 操作の中断や会話の割込みだけで、cleanupプロセスが終了したと判断しません。実行中なら完了を待ち、並行して再実行しません。
3. この作業コピーに属するDiag、常駐サーバー、単独アプリ、Discord・Slack、補助プロセスの残留を確認します。
4. `8090`、`8091`、`8092`、`8093`、`8095`、`8096`、`8098` の待受を確認します。待受がある場合は所有プロセスを照合し、他のプロジェクトや一般アプリを停止しません。
5. `.cleanup_stop_request.json` が消えていることを確認します。停止通知ファイルが残る場合は、所有プロセスと監視処理が終了したことを確認してから整理します。

Codexなどの操作支援プロセスは、作業ディレクトリを引数に持っていてもAiDiy本体とは限りません。実行ファイル・入口・親子関係で区別します。

## 2. 不要フォルダを確認する

対象は、選択したcleanupで削除される依存関係・生成物と、全体cleanupが整理する一時領域です。

- `node_modules`、`.venv`、`venv`、ビルド出力。
- `__pycache__`、`.pytest_cache` などの実行キャッシュ。
- `temp`、`_temp`、`.temp`、`tmp`、作業用の `test`、`_test`、`.test`。
- `.aidiy_cache/selftest/` の旧作業結果、空フォルダ、撮影・PDF確認の中間生成物。
- 解除対象だったランチャー、拡張登録、停止通知の残り。

`dist` という名前だけでは削除しません。manifestや実行コードが参照する同梱配布物は必要です。例えばDiagの `static/` やHermesプラグインの配布画面は、再生成方法と利用箇所を確認して判断します。

再帰削除前に絶対パスを解決し、意図した作業コピー内であることを検証します。シンボリックリンク・ジャンクションの参照先や、保存版・Git管理情報へ入りません。空フォルダは空であることを確認して削除します。

## 3. 不要テストプログラムを確認する

一度だけ使った撮影、画像変換、比較、データ作成、調査用スクリプトは、結果を正式資料へ反映した後に削除します。ソース直下や各モジュール内に作業用プログラムが残っていないかも確認します。

`checks/`・`tests/` の正式な回帰テストは、名前や作成日だけで削除しません。現行機能の仕様・不具合再発防止を検証するものは維持します。廃止機能専用、重複、現行実装と無関係になった試験は、テスト実行設定・import・文書の参照を確認して整理します。

今後も必要な試験手順は、常設テストとして適切な場所へ集約します。正式な試験コードと、一時的な実行結果・ログ・撮影補助のコピーを区別します。


資料の統合・改名・旧版削除は [ナレッジ更新手順](./共通,ナレッジ更新手順.md)、セルフテスト証跡は [説明資料の書き方](./セルフテスト,_説明資料の書き方.md) に従います。資料整理を再試験の成功として記録しません。


### Navigator の停止対象

- 全体 cleanup は削除選択に関係なく、単独 Navigator を事前停止する。IDE の終了では同じ Electron 内の Navigator 子窓も終了する。停止失敗時は削除へ進まない。
- setup / start の共通停止では、この配置先の `aidiy_navi/launch.mjs`、共有入口の `--app navi`、専用 Electron プロファイルとその子孫を強制停止する。Navigator は自動起動しない。
- setup / start は従来どおり IDE / Code を維持する。IDE と同一 Electron プロセス内の Navigator 子窓は、OS の PID だけで単独停止できない。IDE を巻き込む強制終了は行わない。独立プロセスの Navigator と混同しない。
- 停止判定の変更は `scripts/checks/test_navi_lifecycle.py` と既存の `test_setup_processes.py` を模擬プロセスで確認する。検証目的で実 cleanup を実行しない。

Navigator のセットアップは既存の IDE 群選択に含む。選択表示・依存準備・起動コマンド登録・再ビルド時の再登録は Console の手前に置く。専用の依存重複導入や自動起動は行わない。
