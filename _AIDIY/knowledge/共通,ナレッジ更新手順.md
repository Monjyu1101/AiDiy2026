# ナレッジ更新手順

> 文書: `共通,ナレッジ更新手順.md` | 実装: `AGENTS.md`, `_AIDIY.md`, `CLAUDE.md`, `_AIDIY/knowledge/_index.md`

## このメモを使う場面

- 再利用できる知見を追加・統合し、廃止された説明や重複を削除する。
- AGENTS と HowTo の役割を揃え、実装変更後の文書を確認する。
- 再修正時に関連ソースと検証方法を探す。

## 文書の役割と同期元

| 保存先 | 残すもの |
|--------|----------|
| `_AIDIY.md` / `CLAUDE.md` | 同一内容の最小入口。詳細仕様や手順は追加しない |
| ルート `AGENTS.md` | 全体概要、構成、下位文書と人間向け紹介資料への案内 |
| 下位 `AGENTS.md` | モジュールの概要、実装入口、HowTo へのリンク |
| `docs/` | 業務機能開発ガイド（主に HTML） |
| `_AIDIY/knowledge/` | コア機能の HowTo、判断基準、注意点、再検証方法 |
| `_AIDIY/histories/` / Git | 過去の変更経緯。現行 HowTo の旧版コピーは作らない |

実装ファイルを最優先の同期元とし、AGENTS と資料の断定をそのまま転記しません。廃止判断はファイル名ではなく、追跡ファイル・入口・呼出し元で確認します。例えば `backend_diag/` は現行の診断実装であり、`frontend_discord/` の現行配置は `frontend_channels/` です。

## 更新・統合手順

1. `_index.md` から対象テーマを探し、既存文書と関連ソースを読む。複数レイヤーなら API 契約から利用側へ確認する。
2. 担当ファイルと依頼範囲を決める。文書整理の依頼を本体コード・設定・DB変更の許可と解釈しない。既存の未コミット編集を維持する。
3. 同じ手順は一つの正本へ統合する。1見出しで収まる知見のために別文書を作らない。異なる目的の手順・試験条件は無理に統合しない。
4. 有効な固有手順、判断基準、検証条件は残す。廃止機能、誤った断定、途中経過、完了報告、重複一覧は削除する。固定コミットの調査結果はその版の証拠と明示し、現在も未修正とは再確認なしに断定しない。
5. AGENTS に混在した有効な HowTo はテーマ別文書へ移し、元には参照だけを残す。
6. 改名・削除時は索引、関連文書、実装内の文書参照を更新する。`_old.md`、日付付き退避、バックアップコピー、旧版へのリダイレクト文書は作らない。履歴は Git で確認する。
7. 文書・リンクの確認、静的検査、自動テスト、実画面・実AI接続の検証を分けて報告する。過去の成功を今回の実行結果へ転記しない。

コードの不具合修正と、正常動作を維持する整理・改善案も区別します。未採用の提案を実装済み仕様として書かず、採否・修正の承認は別に確認します。

## 命名と本文

- 日本語、UTF-8 without BOM で書く。
- ファイル名は `対象モジュール,トピック名.md`。複数モジュールはカンマで連結し、横断事項は `共通` とする。現行モジュールはルート `AGENTS.md` の構成を参照する。
- 索引は `_index.md` に一本化する。「最新変更」「最終修正」用の別索引は作らない。
- セルフテストの冊子・画像・PDF・命名・結果表示は [説明資料の書き方](./セルフテスト,_説明資料の書き方.md) を正本とする。本文を変更したPDFは再生成・表示確認まで行い、未生成なら明示する。
- 日時や試験条件は本文に記載する。ファイル名へ日付、旧版、最新版、変更後などの版管理語を付けない。
- ソース・コマンド・設定キーはコード表記にする。仕様値には同期元を書く。秘密情報の実値は掲載しない。
- コマンドは PowerShell と bash を区別し、目的と前提条件を併記する。通常確認に理由なく `npm run build` を入れない。

```markdown
# トピック名

> 文書: `対象モジュール,トピック名.md` | 実装: `対象/ソースファイル`

## このメモを使う場面

- この手順が役立つ状況
```

## 並列作業

担当範囲を明示し、他の担当の編集を上書きしません。索引と横断リンクは統合担当が最後に整えます。担当外の問題は報告し、別作業のテスト結果や差分を自分の実績に含めません。

## 編集後の検証

- 変更ファイルをUTF-8で読み、BOM混入を確認する（[BOM対処](./共通,UTF8BOM問題対処.md)）。
- 相対MarkdownリンクはURLデコードとアンカー除去後に存在確認する。`<...>` 形式や括弧を含むパスも扱う。見出しへのリンクは見出し自体も確認する。
- 削除・改名前の文書名を現行文書とソースで検索する。履歴・固定版の引用は機械的に書き換えない。
- ソース参照は実在確認に加え内容も照合する。生成物・例示・廃止パスの比較例は現行入口と区別する。
- `_AIDIY.md` と `CLAUDE.md` を変更した場合は同一内容を維持する。
- `git diff --check` と対象差分で空白エラー・意図しない削除・既存編集の消失を確認する。Git管理外ではGit差分だけを根拠にしない。
- 資料と画像・PDFの対応、未参照資産を確認する。現行セルフテスト証拠を古い日付だけで消さない。

MCPバックアップは文書の旧版を増やす代替ではありません。利用不可でも対象差分の確認を続け、失敗は正確に報告します。設定・DB・既存の利用者バックアップは文書整理の削除対象ではありません。
