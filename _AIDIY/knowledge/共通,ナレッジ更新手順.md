# ナレッジ更新手順

> 文書: `共通,ナレッジ更新手順.md` | 実装: `_AIDIY/knowledge/_index.md`

## このメモを使う場面

- `_AIDIY/knowledge` の既存メモへ知見を追記する
- 新規ナレッジファイルを作るか、既存ファイルへ統合するか判断する
- 作業履歴や一時メモがナレッジに混ざらないよう整理する
- フォルダ確認結果の根拠と、文書の検証範囲を明確にする

## 基本方針

`_AIDIY/knowledge` は、AiDiy2026 で再利用できる修正知見を残すためのプロジェクト専用フォルダである。日々の作業記録ではなく、次回以降の実装・検証・レビューでそのまま使える HowTo、判断基準、注意点だけを残す。

## 残す内容

- このメモを使う場面
- 関連ファイル
- 手順
- 判断基準
- 注意点
- 確認方法
- 現行仕様の同期元

## AGENTS 整理時の扱い

- `AGENTS.md`、下位 `AGENTS.md`、`_AIDIY.md`、`CLAUDE.md` の整理は [`共通,AGENTS整理手順.md`](./共通,AGENTS整理手順.md) を優先する。
- AGENTS 側は概要、構成、参照先に絞る。
- 起動、追加、検証、トラブル対応などの HowTo は `_AIDIY/knowledge` へ転記してから AGENTS 側を短くする。
- `_AIDIY.md` と `CLAUDE.md` は同一内容の最小入口にする。

## 残さない内容

- 作業日時、作業者名、単発の変更履歴
- 「対応した」「対応済み」など一時的な表現
- 実行しただけのコマンド羅列
- 未確認の推測
- TODO だけの見出し
- 同じ意味の長い説明や背景説明
- アプリ本体の仕様変更と混同するメモ

必要な検証コマンドは、何を確認するためのものか分かる形で残す。

## 更新前の確認

1. 担当ファイルを固定する。
   - 並列作業時は担当ファイル以外を変更しない。
   - `_index.md` は親エージェントが最後に統合するため、サブエージェントは原則触らない。
   - `_最終変更.md` は履歴ではなく再修正時の入口として扱い、直近作業の要約を蓄積しない。
2. 既存ファイルを読む。
   - 同じテーマの重複ファイルを増やさず、既存ファイルへ統合する。
   - 既存編集を戻さず、内容の衝突がある場合は現行実装を確認して整合させる。
3. 文字コードは UTF-8 without BOM を維持する。
4. 本体修正を伴う場合は、作業前に `_index.md` と `_最終変更.md` を参照する。

## 書き方

### 確認依頼と自己改善書き込みの区別

- 「フォルダ内の確認」は、ファイル一覧と `_index.md` を読み、類似手順を特定する確認作業である。本体を修正したことにはしない。
- 完了通知後の自己改善依頼では、提示された変更ファイルと既存テーマの記録を照合し、現行ソースから確認できる修正判断・関連箇所・次回の確認方法だけを統合する。過去の「検証完了」を今回のテスト実行結果として転記しない。
- 書き込み先は依頼で指定された `_AIDIY/knowledge` 配下に限定する。本体コード、テスト、設定、バックアップ名、再起動指示ファイルは変更しない。
- `_最終変更.md` には最新テーマの修正要点と再確認先を整理し、履歴を蓄積しない。依頼に拡張子なしの `_最終修正` も明示された場合は、その名前を勝手に置換せず、`_最終変更.md` への参照として用意する。詳細はテーマ別メモへ集約する。
- Git 管理外なら `git diff` を検証根拠にしない。編集ツールが示す対象・差分、UTF-8での内容確認、追加したリンク先の存在確認で、実施範囲と記録の整合性を確認する。

### フォルダ確認結果の根拠と記録の整合性

1. `_AIDIY/knowledge` の一覧と `_index.md` を確認し、依頼に関係するテーマ別メモを読む。件数を報告する場合は、直下か再帰か、拡張子なし・旧版ファイルを含むかを明確にし、一覧の省略・上限に達していないことを確認する。過去の件数を固定値として転記しない。
2. 確認対象を依頼文から切り分ける。引用された過去の依頼・最終応答・変更一覧は照合の材料であり、今回の本体編集やバックアップ名変更の指示ではない。
3. 索引のリンク先が存在するだけでなく、案内した見出しと内容がテーマ別メモにあるか確認する。音声仕様など本体の挙動を再評価する場合だけ関連ソースへ進み、文書の存在確認を動作検証と同一視しない。
4. `_index.md`、`_最終変更.md`、拡張子なしの `_最終修正` とテーマ別メモの参照を揃える。`_最終修正` は `_最終変更.md` への案内に留め、詳細や履歴を複製しない。最新テーマを切り替える場合も、既存テーマの知見はテーマ別メモに残す。
5. 自己改善では、確認結果の羅列ではなく、上記の判断基準・関連箇所・次回の検証方法を既存メモへ統合する。報告では文書確認、テスト実行、実接続確認を区別し、実施していない検証や再起動を完了扱いにしない。

関連箇所:
- `_index.md`: 「迷ったときの入口」「ドキュメント・共通」。
- `_最終変更.md`: 「最終変更テーマの確認入口」。
- `_最終修正`: 同階層の `_最終変更.md` への参照。
- `frontend_discord,Discord接続変更手順.md`: 「出力チャンク境界と末尾処理の再修正チェック」。Discord 音声の詳細はここに集約し、フォルダ確認手順へ重複転記しない。

### 記述上の注意

- 日本語で簡潔に書く。
- ファイル名、コマンド、パス、設定キーはバッククォートで囲む。
- 手順は次回の作業者がそのまま実行できる順番にする。
- 「何をしたか」ではなく「次にどう判断するか」を書く。
- 仕様値を書くときは同期元を併記する。
  - 例: JWT 600分は `backend_server/auth.py`
  - 例: MCP は Windows 19 / Linux・macOS 18サーバー。同期元は `backend_tools/tools_main.py`
- 古い状態の断定を避け、不明な場合は「現行実装を確認する」と書く。
- Windows PowerShell 前提と bash 前提は本文またはコードブロックで分ける。

## 並列作業時のルール

- 親エージェントがサブエージェントごとの担当ファイルを明示する。
- サブエージェントは担当ファイル内に完結する内容だけを書く。
- `_index.md` は全担当ファイルを確認したあとに親エージェントがリンク整理する。
- `_最終変更.md` は履歴ではなく再修正時の入口に限定する。直近作業の要約は残さない。
- 担当外ファイルに差分や問題を見つけた場合は編集せず、最終報告に残す。

## 新規ナレッジ作成の判断

- 既存テーマに 1 見出しで収まる内容は既存ファイルへ追記する。
- 複数回参照される独立手順、チェックリスト、障害対処は新規ファイルにしてよい。
- ファイル名は日本語で、内容が分かる名詞句にする。
- 並列作業のサブエージェントは、`_index.md` へのリンク追加候補を最終報告に書く。

## 編集後の検証

```powershell
$files = @(
  "_AIDIY/knowledge/対象ファイル.md"
)

# BOM 確認
foreach ($file in $files) {
  $bytes = [System.IO.File]::ReadAllBytes((Resolve-Path $file))
  if ($bytes.Length -ge 3 -and $bytes[0] -eq 0xEF -and $bytes[1] -eq 0xBB -and $bytes[2] -eq 0xBF) { $file }
}

# 未整理表現は、仮置き見出し・一時対応文・単発履歴が残っていないか本文を確認する
```

相対 Markdown リンクを書いた場合は、リンク先が存在するか確認する。存在確認できないものはリンクではなくコード表記のパスに留める。

## MCP バックアップ失敗時

MCP バックアップが使える場合は、編集前後の差分確認に利用する。失敗しても作業を止めず、担当ファイルの通常確認を優先する。

- 失敗した MCP 名、対象ファイル、失敗概要を最終報告に短く残す。
- 代替として `git diff -- _AIDIY/knowledge/<担当ファイル>` などで差分を確認する。
- バックアップ失敗を理由に、担当外ファイルを編集したり既存編集を戻したりしない。
