# 会話履歴のプロジェクト識別

> 文書: `backend_server,frontend_ide,frontend_web,frontend_avatar,会話履歴のプロジェクト識別.md` | 実装: `backend_server/core_models/A会話履歴.py`, `backend_server/core_router/A会話履歴.py`, `backend_server/core_router/AIコア.py`, `backend_server/会話履歴パス.py`, `backend_server/AIコア/AI履歴コンテキスト.py`, `frontend_web/src/api/websocket.ts`, `frontend_avatar/src/api/websocket.ts`, `frontend_ide/host/src/code-connection.ts`

## このメモを使う場面

- 同じプロジェクトの Chat / Code の会話をセッション横断で取得・分析する。
- 会話履歴へ保存するプロジェクトと、選択ファイル・実行フォルダの違いを確認する。
- 非同期応答やプロジェクト切替で履歴の所属が混ざらないように変更する。

## 保存項目と同一性

`A会話履歴.プロジェクトパス` は、要求受付時のセッションの `CODE_BASE_PATH` が指すプロジェクトルートの絶対パス。フォルダ名だけでは識別せず、選択中ファイルやサブフォルダのパスも代入しない。

- Windows のドライブ絶対パス・UNC は区切りを `/` に統一し、小文字化して `.` / `..` と末尾区切りを整理する。
- POSIX の絶対パスは大文字小文字を区別する。
- シンボリックリンク・別ドライブ割当・別マシンの同一リポジトリを同一と推測しない。フォルダ移動後のパスは別識別になる。
- 所属を確定できない場合は `NULL`。現在のプロジェクトで過去の行を補完しない。
- 本カラムは分析用の識別情報であり、アクセス権限やファイル操作許可を与えるものではない。

現行モデルから新規DBを作る。旧DBへの列追加・自動変換・旧テーブルフォールバックは行わない。DB構造変更時の再作成は、利用者が既存データの扱いを確認して実施する。

## 入力から保存まで

Web / Avatar の Chat・Code は接続時に確認した `CODE_BASE_PATH` を入力メッセージの `プロジェクトパス` に付ける。Avatar の別ウィンドウは中継前に表示中のプロジェクトを固定する。IDE / VS Code / 単独起動のオンラインCodeは接続対象のプロジェクトを付ける。

バックエンドは受信値とセッションのルートを照合する。相対 `CODE_BASE_PATH` は `backend_server` 基準で解決し、不一致は実行せず画面へエラーを返す。項目未送信のクライアントも、確認できるセッションのルートを使う。

受付時の値をキューにコピーし、Chat / Code ワーカーの要求コンテキストへ固定する。最終応答・検証結果・添付履歴・要求内の内部ツール呼出しは同じ値を引き継ぐ。保存時点の可変なセッション設定から引き直さない。

Chat / Code の待機中・処理中は同一セッションのプロジェクト変更を拒否する。受付とキュー投入の間に切替が競合した要求も、別プロジェクトで実行せず再送を案内する。

音声入力認識はバッファ受付時の値を保持する。切替をまたいだバッファは所属を推測せず `NULL` とする。Live字幕の既存の保存範囲は別問題で、本項目の追加によって未保存の字幕や音声本体を新たに記録するわけではない。

## MCP / REST からの通常会話

`aidiy_chat_llms` の `chat_llms_run` / REST `run` と、`aidiy_code_agents` の `code_agents_run` / REST `run` は、共通の `backend_tools/tools_proc/conversation_history.py` を通して同じ `A会話履歴` へ記録する。Diag 専用の登録処理ではない。

- 呼出し時の明示的な `project_path` を正規化して両行へ固定する。相対パスは実行前に拒否し、省略時は設定値・実行結果のパスで補完せず `NULL`。プロジェクト別分析をする呼出し元は絶対パスを渡す。
- DBセッションは呼出しごとに一意な `mcp_chat_<UUID>` / `mcp_code_<UUID>`。Chat はチャンネル `0`、Code は `1`、入力はシーケンス `1` / `input_text`、正常な最終応答は `2` / `output_text`。同時呼出しでも入力・応答の対応を混同しない。
- Chat の `session_id` はモデル文脈の継続用であり、このDBセッションとは別。CLI自身の履歴や表示用JSONの保存仕様も変えない。
- 入力のDB保存に失敗した場合はAIを開始しない。実行失敗・キャンセルは `error` 行で区別し、正常なAI応答として予測へ渡さない。入力だけの未返信ターンが残る場合はある。
- `history_saved=true` は入力と正常な最終応答がDBへ確定した意味。`false` は「何も保存されていない」意味ではないため、入力保存は `history_input_saved` で確認する。`history_session_id` / `history_project_path` は保存先の識別情報。
- AI完了後に保存が失敗した場合は `status=NG` / `history_saved=false` / `history_error` を返すが、生成結果は保持し、AI自体の結果を `execution_status` に残す。特に Code の `execution_status=OK` はファイル変更が完了している可能性があるため、保存失敗だけを理由に自動再実行しない。
- `backend_server/会話履歴記録.py` は現行テーブルへパラメーター化INSERTするだけ。`mode=rw` でDB不在時の作成を防ぎ、列追加・旧構造互換は行わない。接続待ちは最大1秒で、専用スレッド内で完結する。キャンセル時も進行中commitの確定を待ち、遅延書込や二重登録を防ぐ。

通常のAIコアは従来の保存経路を維持し、MCP境界でのみ追加するため二重保存しない。`aidiy_chat_completions` の `complete_async` と内部予測 `aidiy_prediction_llms` はこの境界を通らず、予測の入力・結果を会話履歴へ追記しない。

## 取得・分析

`POST /core/A会話履歴/一覧` に `プロジェクトパス` を指定すると、セッションをまたいで同じプロジェクトの行を取得できる。`セッションID`・`チャンネル`とも併用できる。`プロジェクトパス`・`セッションID`・`シーケンス`の複合索引を持つ。

```json
{"プロジェクトパス":"C:/work/example", "件数":10000}
```

一覧・単件取得・WebSocket履歴再送には `プロジェクトパス` が含まれる。直接CRUD APIで指定するパスは絶対パスに限り、同じ正規化を適用する。変更APIで省略した場合は既存値を保ち、明示的な `null` / 空文字で解除する。

既存一覧APIの上限は1万件で、ページングはない。全件分析はこの上限に注意する。オフラインCode / Discord CodeのHermes履歴は別ストアであり、このDBへ同期しない。

## 確認観点

- 同一ルートの別セッションが同じ絞込結果に入り、同名別フォルダが混ざらない。
- Windows表記揺れを統合し、POSIXの大文字小文字を維持する。
- 要求コピー後の変更、並行セッション、子タスク、処理中切替でも応答の所属が変わらない。
- 新規の隔離DBで列・索引・登録・取得・フィルタを検証する。実DBや実会話ログをテスト入力にしない。
