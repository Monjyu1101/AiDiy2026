## 起動手順

通常起動はプロジェクトルートで行う。

```powershell
python _start.py
```

`_start.py` は対話形式で、起動するサービスを選択する。`backend_local` はデフォルト No。未起動時は AI設定の `local_chat` 候補から除外される。`command_hermes` は on-demand CLI のため常駐起動対象ではない。`frontend_channels` は既定 No で、Yes の場合は接続パネルを開いて自動接続する。

フロントエンドは Avatar の後、「IDE群(Code / Live / IDE)」の中で Code → Live → IDE を個別選択し、その後に Discord を選択する（既定 No）。セットアップ・cleanup はIDE群を一括選択（既定 Yes）し、`frontend_ide/_setup.py` / `_cleanup.py` が Code / Live のhost → IDEのviewer → 共通UIを管理する。Discordは別項目としてその後に実行する。`frontend_ide/host/_start.py` は `aidiy_code` / `aidiy_live` と同じランチャーをコマンド起動し、作業フォルダはプロジェクトルートにする。Code は待機指定を付けず独立起動し、Live は `--foreground --connect` を渡す。Live はモデル未指定でも保存済み選択（未保存なら Core の既定設定）で1回だけ自動接続し、マイクは OFF のまま。手動で閉じた画面は自動再表示しない。全体起動の終了後も Code / IDE / Discord は継続し、明示的な cleanup では子プロセスも回収する。

個別起動が必要な場合:

```powershell
# Core API
Set-Location backend_server
.venv/Scripts/python.exe -m uvicorn core_main:app --reload --host 0.0.0.0 --port 8091

# Apps API
Set-Location backend_server
.venv/Scripts/python.exe -m uvicorn apps_main:app --reload --host 0.0.0.0 --port 8098

# MCP
Set-Location backend_tools
.venv/Scripts/python.exe tools_main.py

# TaskTeam（`/task/*` と `/team/*`）
Set-Location backend_taskteam
.venv/Scripts/python.exe -m uvicorn taskteam_main:app --reload --host 0.0.0.0 --port 8093

# Hermes CLI
Set-Location command_hermes
.venv/Scripts/python.exe cli_main.py

# frontend_web
Set-Location frontend_web
npm run dev

# frontend_avatar
aidiy_avatar

# frontend_channels
aidiy_discord
```

アバターの `aidiy_avatar` は既存の Electron / Vite 起動処理を使い、どの作業フォルダからでも実行できる。Ctrl+C でアバターを停止する。`python frontend_avatar/_setup.py` で `~/.local/bin` に登録する。依存関係を更新せずランチャーだけ登録する場合は `python frontend_avatar/_setup.py --launchers-only` を使う。`aidiy_avatar --help` は画面やサービスを起動せず使い方を表示する。

`aidiy_avatar` / `aidiy_live` / `aidiy_discord` は二重起動を防止する。再実行で既存の画面・接続・モデルを作り直さない。Avatar は起動処理を OS のファイルロックで排他し、8092 が起動中なら停止せず終了する。Electron 側でも単一起動にする。Live / Discord は GUI・ブラウザ共通のローカル排他（18094 / 18095）を持ち、画面がある場合は再表示する。排他はプロセス終了時に OS が解放するため、強制終了後も手作業でロックを削除する必要はない。

## バックエンド変更の反映

`_start.py` 起動では uvicorn に `--reload` が付かない。コード変更を反映する場合は、次のいずれかを使う。

```powershell
# core_main.py を再起動
New-Item -ItemType File -Force backend_server/temp/reboot_core.txt

# apps_main.py を再起動
New-Item -ItemType File -Force backend_server/temp/reboot_apps.txt

# taskteam_main.py を再起動
New-Item -ItemType File -Force backend_taskteam/temp/reboot_taskteam.txt

# tools_main.py（MCP 8095）を再起動
New-Item -ItemType File -Force backend_tools/temp/reboot_tools.txt

# local_main.py（8096）を再起動
New-Item -ItemType File -Force backend_local/temp/reboot_local.txt
```

各サーバーは自分の `temp/reboot_*.txt` を1秒ごとに監視し、検知するとファイルを削除して終了する。`_start.py` が終了を検知し、15秒後に同じコマンドで起動し直す。AIコアの設定変更で再起動が必要な場合も、同じファイルを書いて再起動する。プロセスを直接終了しても自動再起動されるが、子プロセスごと止まるため reboot ファイルを優先する。backend_tools の `pyproject.toml` に依存を追加した場合は、`uv sync` の後に tools を再起動する。

または個別起動で `--reload` を使う。

## 初期セットアップ

初回または環境リセット時:

```powershell
python _setup.py
```

主な対象:

- `backend_server` の Python 仮想環境と依存関係。
- `backend_tools` の Python 仮想環境と依存関係。
- `command_hermes` の Python 仮想環境と依存関係。
- `backend_taskteam` の Python 仮想環境と依存関係。
- `frontend_web` / `frontend_avatar` の `npm install` と `npm update`。
- `frontend_ide/host` の依存導入、Electron の準備、Code / Live の VSIX 生成と VS Code 拡張機能への配置、`~/.local/bin` への `aidiy_code` / `aidiy_live` ランチャー作成。VS Code CLI が無い場合は単独起動用のコンパイルとランチャー作成だけを行う。ルート選択では `command_hermes` の次に実行する。
- `frontend_channels` の依存導入、Electron の準備、`~/.local/bin` への `aidiy_discord` ランチャー作成、`_config/AiDiy_key.json` の不足 `DISCORD_*` 補完。既定 Yes。

### Windows のランチャーと PATH

各コマンドのランチャー配置処理は、`~/.local/bin` をユーザー PATH に自動登録する。全体セットアップだけでなく、Diag / IDE / Term / Code・Live / Avatar / Hermes / Discord の個別セットアップでも同じ処理を使う。共有処理は `scripts/_setup_path.py`。既存項目・環境変数表記・レジストリの文字列型を保持し、大文字小文字・区切り文字・末尾の区切り・引用符・環境変数展開を考慮して重複を避ける。システム PATH は変更しない。

同じフォルダの `aidiy_diag` / `aidiy_hermes` / `aidiy_ide` / `aidiy_code` / `aidiy_live` / `aidiy_avatar` / `aidiy_term` / `aidiy_discord` に共通で反映される。セットアップの子プロセスには即時反映する。既存のターミナルや VS Code は開き直す。通知を受け取れない環境ではサインインし直す。

自動追加した登録は `~/.local/.aidiy-launcher-path.json` に記録する。クリーンアップは各ランチャーを解除した後、共有 bin が空なら自動追加分の PATH を解除する。個別 cleanup でも確認し、全体 cleanup は他のランチャーの解除が終わった後に再確認する。Avatar も `aidiy_avatar` / `aidiy_avatar.cmd` を解除対象とし、別コピーの起動先を指すランチャーは保持する。元から存在した PATH 登録、後から追加された別の PATH 項目、別コピーのランチャーや他ツールが使っている共有 bin の登録は保持する。記録ファイルは解除成功時だけ削除する。

「コマンドが見つからない」場合は、まず `Get-Command aidiy_diag` と `Test-Path "$HOME/.local/bin/aidiy_diag.cmd"` で PATH とランチャーを切り分ける。本体の切り分けは `node backend_diag/diag_main.mjs` を使う。登録・解除の検証は `python -B -X utf8 scripts/checks/test_setup_path.py` で行い、実際のユーザー PATH は変更しない。8コマンドの配置・PATH による検出・個別解除・最後の PATH 解除までを一時フォルダと模擬レジストリで確認する。GUI や外部サービスは起動しない。

### macOS / Linux のランチャーと PATH

同じ `scripts/_setup_path.py` が macOS / Linux にも共通の登録を行う。macOS は zsh の `.zprofile` / `.zshrc`、bash のログイン設定と `.bashrc` に、Linux は bash のログイン設定と `.bashrc` に登録する。Linux で `$SHELL` が zsh の場合は `.zprofile` / `.zshrc` も対象とする。zsh の `ZDOTDIR` があればそちらを使う。bash は既存の `.bash_profile` → `.bash_login` → `.profile` の優先順位を守り、新規ファイルによって既存のログイン設定を隠さない。該当ファイルがなければ macOS は `.bash_profile`、Linux は `.profile` を作る。

登録は識別コメントで囲み、既存内容をそのまま残して追記する。PATH が既にランチャーフォルダを含む場合も、別の新しいシェルで使えるよう永続設定を確認する。シェル内では重複を避け、空白・引用符・`$` 等を含むパスを引用する。Hermes も独自の新規 PATH 登録をやめてこの共通処理を使う。ランチャーは LF と実行権限を設定する。

自動追加した内容は Windows と同じ `~/.local/.aidiy-launcher-path.json` に記録する。共有 bin に残したコマンドや他ツールがある間は保持し、空になったときだけ自動追加した部分を解除する。後から書かれた設定は保持し、自動生成した空の設定ファイルだけを削除する。書込権限エラーや自動登録部分の手動変更を成功扱いにせず、記録を残して再試行できるようにする。

依存導入やビルドを繰り返さず8コマンドの登録だけを修復する場合は、プロジェクトルートで `python3 _setup.py --launchers-only`（Windows は `python _setup.py --launchers-only`）を実行する。依存物は事前に通常セットアップ済みであること。完了後に新しいターミナルを開く。現在のターミナルで直ちに使う場合は `export PATH="$HOME/.local/bin:$PATH"` を実行する。`command -v aidiy_diag` でランチャー検出、`aidiy_diag --help` でコマンド起動、`aidiy_diag --browser` で Electron と切り分ける。

検証は `python3 -B -X utf8 scripts/checks/test_setup_posix.py`。一時 HOME で Mac / Linux の登録先・再実行・既存設定保持・共有 PATH 解除・修復専用経路を確認する。POSIX では実シェルを使って8コマンドの LF・実行権限・PATH 検出・引数転送・解除も確認する。起動先は合成スクリプトであり GUI や本物のサービスは起動しない。Windows では実シェル部分をスキップし、Linux / macOS で実行する。

## git pull 後の Node.js 系再配置

`python _setup.py` の最初の選択で `r`（大文字 `R` も可）を押します。既存の `y`（項目選択）、`n`（中止・既定）、`a`（既定値で全体セットアップ）はそのままです。

`r` は Diag本体/UI、Web、Avatar、IDE共通UI・Code/Liveホスト・ビューア、Discord の依存を `npm install --include=dev --no-fund --no-audit` で同期します。既存の `node_modules` を一括削除する `npm ci` や、宣言範囲の最新版へ進める `npm update` は行いません。pullされた `package.json` / lockfile の変更や不足依存は同期対象です。Node.js/npmが無ければ終了し、OSツールを自動導入しません。

依存が揃っていても、Diag UI、Web、Avatar、Code/Live/IDE共通UI、Discordパネルを必ず既存のビルド処理で再生成します。Code/LiveはVS Code CLIがあればVSIXを再生成・配置し、無ければ単独画面をコンパイルします。共通Vueはhostのビルド内で生成し、二重ビルドを避けます。`aidiy_diag` / `aidiy_avatar` / `aidiy_term` / `aidiy_code` / `aidiy_live` / `aidiy_ide` / `aidiy_discord` のランチャーも既存処理で再配置します。

Electron本体は既存配置・他画面の同版・共有ZIPを優先して再利用し、不足時のみ取得します。GUIなし、Codespaces、`ELECTRON_SKIP_BINARY_DOWNLOAD=1` では本体の準備を省略します。Python環境・モデル・DB・MCP/Discord設定補完・グローバルAI CLI更新・Diag headlessは実行しません。アプリや常駐サービスも起動しません。Hermes本体の更新はPythonを含む通常セットアップで扱います。

失敗時は項目名を表示して後続を止め、終了コード1を返します。すべて成功したときだけ完了扱いになります。ネットワークを使った実導入なしの検証は `python -B scripts/checks/test_node_refresh.py`、既存経路の回帰は `backend_diag/checks/check_setup.py` と `frontend_ide/host/checks/test_setup.py` / `frontend_ide/viewer/checks/test_setup.py` を使います。

## 依存関係

```powershell
# backend_server
Set-Location backend_server
uv sync --upgrade
uv add <package>

# command_hermes
Set-Location command_hermes
uv sync --upgrade

# backend_taskteam
Set-Location backend_taskteam
uv sync --upgrade

# frontend_web
Set-Location frontend_web
npm install
npm update
npm run type-check

# frontend_avatar
Set-Location frontend_avatar
npm install
npm update
npm run type-check

# frontend_ide/host（Code / Live の VSIX 生成・配置とランチャー作成を含む）
Set-Location frontend_ide/host
python _setup.py

# frontend_channels（Electron 準備とランチャー作成を含む。ビルド不要）
Set-Location frontend_channels
python _setup.py
npm run check
```

`npm update` は `package.json` の宣言範囲内で依存関係を最新版へ更新する。メジャー更新時は `package.json` と `package-lock.json` を更新し、型チェックと `npm audit` を行う。現行の `vue-tsc 3.3.11` は TypeScript 7 に未対応のため、TypeScript は動作可能な最新の 5.9.3 を使用する。

`npm run build` は `dist/` を生成するため、明示指示がある場合または Docker 反映が必要な場合に限定する。

### backend_local の tokenizers ビルドエラー

`uv sync --upgrade` で `transformers 4.12.2` / `tokenizers 0.10.3` が選ばれ、
`can't find Rust compiler` になる場合は、まず `backend_local/pyproject.toml` の依存範囲を確認する。
Hub 2 系と現行の `tokenizers` は互換性がなく、範囲未指定では古い `transformers` へ戻ることがある。
Gemma 4 に対応する `transformers>=5.5,<6` と、`huggingface-hub>=1.5,<2` を組み合わせる。
依存範囲を変更したら `uv.lock` も更新する。

```powershell
Set-Location backend_local
uv sync --upgrade
uv run --locked python -c "from importlib.metadata import version; print({p: version(p) for p in ('transformers', 'tokenizers', 'huggingface-hub')})"
```

Windows x64 / Python 3.13 の依存が wheel だけで解決できるかは、インストールせず確認できる。

```powershell
uv pip compile pyproject.toml --python-platform x86_64-pc-windows-msvc --python-version 3.13 --only-binary :all:
```

### Electron の共通セットアップ

`frontend_avatar/_setup.py`、`frontend_ide/host/_setup.py`、`frontend_ide/viewer/_setup.py`、`frontend_channels/_setup.py` は `scripts/_setup_electron.py` を共用する。npm install / update / rebuild と IDE ビューアの npm ci は `ELECTRON_SKIP_BINARY_DOWNLOAD=1` を付け、Electron の取得を共通処理へ集約する。他の依存のインストールスクリプトは通常どおり実行し、`--ignore-scripts` で復旧した場合は Electron の準備後に `npm rebuild` を行う。

IDE ビューアの postinstall で `TypeError: fetch failed` が出た場合は、`frontend_ide/viewer/_setup.py` が共通処理を使う版か確認する。修正済みのソースでは `python frontend_ide/viewer/_setup.py` で依存を再導入し、同じバージョンの配置済みバイナリまたは共有 ZIP を再利用する。Web 専用環境と明示的な `ELECTRON_SKIP_BINARY_DOWNLOAD=1` 指定時は本体を取得しない。共有処理でも取得に失敗する場合は、表示された接続エラーと GitHub リリースへの接続を確認する。

IDE ビューアと Discord は `npm ci` の後に `npm update electron` を実行し、Electron を宣言範囲内の最新版へ更新してからバイナリを準備する。Avatar / Code・Live は共通処理の `npm install` → `npm update` で更新する。4プロジェクトの指定は `^44.7.0` で、44系のマイナー・パッチ更新を取得し、45系以降への更新は依存範囲を変更して行う。IDE ビューアだけを完全固定に戻したり、更新前にバイナリを準備したりすると、古いロック版を再取得するため注意する。

準備は次の順で行う。

1. 対象プロジェクトの配置済みバイナリを確認し、必要なら `path.txt` だけを修復する。
2. 他のフロントエンド（Avatar / VS Code / IDE ビューア / Discord）に同じバージョンがあれば、その `dist` をコピーする。
3. `_cache/electron/electron-v<version>-<platform>-<arch>.zip` があれば再展開する。
4. まだ取得されていない場合だけ、GitHub の Electron リリース ZIP を Python で取得する。

ZIP は取得完了後に共有キャッシュへ保存する。バージョンが異なるものや未完了の ZIP は再利用しない。各プロジェクトの `dist` は別々に配置し、一方の更新・削除が他方の実行ファイルへ影響しないようにする。接続・読み取りのタイムアウトは30秒、取得中は約2秒間隔で取得量と速度を表示する。バイナリ取得の自動再試行は行わない。共有 ZIP は `node_modules` の削除後も残るため、再セットアップ時に利用できる。

Electron の依存範囲は4プロジェクトの `package.json` でそろえ、更新時は各 `package-lock.json` の解決バージョンもそろえる。セットアップでは共有 ZIP を自動削除しない。旧版・新版・別 OS・CPU 向けのキャッシュをすべて保持し、必要な版を再利用する。壊れた同名 ZIP も先に削除せず、再取得と検証が成功してから置き換える。取得失敗時は既存ファイルを保持する。キャッシュに新しい版があっても、npm パッケージと異なる版のバイナリだけを流用せず、先に npm でバージョンを揃える。

共通処理の確認:

```powershell
python -m unittest discover -s frontend_ide/host/checks -p test_setup.py
python -m unittest discover -s frontend_ide/viewer/checks -p test_setup.py
```

## クリーンアップ

不要な仮想環境、`node_modules`、`dist`、キャッシュ、DB を整理する場合:

```powershell
python _cleanup.py
```

削除対象は対話形式で確認される。ルート `backup/` や DB を消す場合は復旧材料が不要か確認する。

何らかのクリーンアップを選ぶと、ファイル削除へ入る前に全常駐サービスの `_start.py` 停止処理が呼ばれる。停止対象は Web `8090`、Core `8091`、Avatar `8092`、TaskTeam `8093`、Tools `8095`、Local `8096`、Apps `8098` で、選択した削除対象だけには限定しない。Avatar の残留 Electron プロセスと、待受ポートを持たない Discord Bot（`discord_processes.py` で実行入口を照合）も停止する。ルート `_start.py` が監視中の場合は、全常駐サービスを自動再起動対象から外し、クリーンアップ中や完了直後に再起動しないようにする。

## DB 管理

DB ファイル:

```text
_data/AiDiy/database.db
```

開発用に全テーブルを作り直す場合:

1. `_start.py` や個別起動中のサーバーを停止する。
2. SQLite Browser / DBeaver など DB 接続ツールを閉じる。
3. `_data/AiDiy/database.db` を削除する。
4. backend を再起動する。

初期データは、対象レコードが未存在の場合のみ投入される。既存DBでは自動更新されない。

スキーマ差分を既存DBへ反映する場合は、DB削除ではなく [`backend_server,スキーマ変更手順.md`](./backend_server,スキーマ変更手順.md) を使う。

## ポート競合

`_start.py` は起動前と Ctrl+C 終了時に、常駐サービス（local 8096 / tools 8095 / core 8091 / apps 8098 / task・team 8093 / Web 8090 / Avatar 8092 と残留 Electron）、Live の単独実行、tools の MCP 接続を停止する。aidiy_code / aidiy_ide / aidiy_discord は本体とその子孫を停止対象から外し（`keep_code=True` / `keep_dev=True` / `keep_discord=True`）、選択や起動元に関係なく継続する。保護する子孫を判別できないときは tools の MCP 接続を止めない。全体起動の Code / Discord ランチャーには `--wait` を付けず、IDE も独立したプロセス・セッションとログファイル出力を使う。IDE の URL / ログは `frontend_ide/viewer/out/aidiy_ide/` に保存し、自動再起動はしない。`_cleanup.py` は Code / Live / IDE / Discord を含めて停止し、監視中の明示的な cleanup 要求も `keep_standalone=False` で停止する。停止手順は `_cleanup.py` の `stop_all_services()` と共通で、`_start.py` では停止失敗を警告して続行し、`_cleanup.py` では残りを止めたうえで削除を中止する。

手動確認:

```powershell
netstat -ano | findstr :8091
taskkill /PID <pid> /F
```

## よくある問題

| 症状 | 主な確認先 |
|------|------------|
| `address already in use` | ポート残留を `netstat` で確認する |
| 文字化け | ファイルが UTF-8 か、PowerShell で `Get-Content -Encoding UTF8` を使っているか確認する |
| 401 | JWT期限、Storage、`認証延長ルール.md` を確認する |
| CORS | `core_main.py` / `apps_main.py` の allowed origins と Vite port を確認する |
| Python `ModuleNotFoundError` | 対象 backend で `uv sync --upgrade` を行う |
| npm package 不足 | 対象 frontend で `npm install`、続けて `npm update` を行う |
| `database is locked` | SQLite Browser / DBeaver などの接続を閉じる |
| テーブル不足 | backend 再起動、model import、`apps_models/__init__.py`、`apps_crud/__init__.py` を確認する |
| backend 変更が反映されない | `_start.py` 起動では `--reload` なし。reboot ファイルまたは個別起動を使う |
| M系一覧エラー | frontend は V系一覧を使うため、M系追加時は V系エンドポイントも作成する |

## 起動ログの確認

- `_start.py` は子プロセスの出力を行単位でUTF-8デコードし、サービス名を行頭に1回付ける。読み取りの1024バイト境界で日本語をデコードしたり、行途中にサービス名を挿入したりしない。確認は `python -m unittest discover -s scripts -p test_start_output.py` で行う。
- ffmpeg / ffprobe / ffplay の未インストール、OBS の未起動、任意のAIベンダーのAPIキー未設定は、それぞれの機能が利用できないことを示す。使わない機能の導入・設定は不要。
