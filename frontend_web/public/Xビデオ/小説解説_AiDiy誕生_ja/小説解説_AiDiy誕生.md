>
> 目指す姿は、ただ一つ。
> 業務をやっている本人が、自分の言葉で話しかけるだけで、
> 自分のシステムが育っていく世界。
>
> これは、その世界にたどり着くために、
> 一人の開発者と AI が積み上げた、この一年あまりの記録である。

## 序章 — 一枚のHTML（2025年 夏）

はじまりは、驚くほど素朴だった。

まだ「AiDiy」という名前すら無かった頃。
そこにあったのは、FastAPI という Python の小さな骨組みと、
一枚の HTML と、素の JavaScript だけ。

*(FastAPI = Python でウェブの裏側を作る道具。
素の JavaScript = 便利な仕組みを何も使わない、生のブラウザ用言語)*

ビルドツールもない。フレームワークもない。
`<script>` と書いて、その中に直接ロジックを流し込む。
ウェブ開発を少しでもかじった人なら、思わず眉をひそめる作りである。

**それでも、そこで動いていた機能は、いまとほとんど同じだった。**

日本語でテーブルを作り、日本語で API を叩き、日本語のキーが返ってくる。
チャットがあり、音声があり、コード支援があった。

やりたいことは、最初から全部そこにあった。
足りなかったのは、器のほうだけだったのだ。

### そして、構造もすでにそこにあった

驚くべきは、機能だけではない。

**いまの構造の源流が、この素朴な一枚の中に、すでに引かれていた。**

サーバーは、一本ではなかった。**複数に分かれていた。**
そして——ここが肝心なのだが——

**業務システムの共通部分と、個別のアプリ部分が、すでに切り離されていた。**

どこの会社でも要る「利用者」「権限」「採番」のような土台。
その会社にしか要らない「配車」「生産」「在庫」のような業務。

**この二つを、混ぜない。**

なんのために。

テンプレートとして配るものと、
現場が自分の言葉で育てていくものは、**別だからである。**

土台に手を入れずに業務を足せるなら、
配った先で何を作られても、土台は壊れない。
逆に土台を直せば、その恩恵は全部の業務に一度に届く。

「ユーザーによるシステム開発」を本気で考えるなら、
この線引きは、あとから引けるものではない。

一枚の HTML と素の JavaScript。
道具立ては驚くほど貧しかったが、
**引くべき線は、もう引かれていた。**

### なんのために、日本語だったのか

理由は、この物語のすべてを貫く一行に集約される。

> **日本語で AI と会話するなら、コードの変数名も日本語であるべきだ。**

当たり前のことを言っているようで、これは相当に過激な主張である。
世界中のほぼ全てのコードが、この逆をやっているからだ。

想像してほしい。
現場の人が、AI にこう言う。「配車区分を追加したい」。
AI は考えて、こう書く。

```python
class DispatchCategory(Base):
    __tablename__ = "m_dispatch_category"
```

ここで、静かに何かが失われた。

「配車区分」が `DispatchCategory` に翻訳されたのだ。
翻訳したのは AI である。
だが、その翻訳が正しいかどうかを、**頼んだ本人には確かめようがない。**

`dispatch` か `delivery` か `assignment` か。
`category` か `type` か `classification` か。
選ぶのは AI であり、次に頼んだときには別の単語かもしれない。

そして翌日、その人はまた「配車区分」と言う。
AI は、昨日の自分がつけた英語を思い出し、対応表を引き直す。
引くたびに、ズレる余地が生まれる。
同じ概念に三つの綴りが割り当てられ、システムは静かに歪んでいく。

**ならば、翻訳という工程ごと消してしまえばいい。**

```python
class M配車区分(Base):
    __tablename__ = "M配車区分"
    配車区分ID = Column(String)
```

言った言葉が、そのままコードに立っている。
`POST /apps/配車区分/一覧` を叩けば `{"配車区分ID": "01"}` が返り、
`M配車区分一覧.vue` がそれを描く。

現場の人は、自分の言葉をコードの中に目で見つけられる。
AI は、聞いた言葉のまま検索して、該当箇所へ一直線に辿り着ける。

**両者のあいだから、翻訳が消える。**

これは「読みやすさ」の話ではない。
AI と人間が同じ語彙を共有しているか、という設計の問題である。
語彙がズレていれば、どんなに賢い AI も、ズレた分だけ間違える。

### なんのために、「日本語」でなければならなかったのか

もう一つ、理由がある。
そしてこれは、日本語という言語そのものの性質にかかわる話だ。

**日本語は、四つの文字を一つの文の中で混ぜられる。**

ひらがな。カタカナ。漢字。そして、英字。
この四つが、境目で衝突せず、シームレスに同居できる。
世界の言語を見渡しても、かなり珍しい性質である。

これがコードの上で、思わぬ効き方をする。

```python
class M配車区分(Base):
    __tablename__ = "M配車区分"
    配車区分ID = Column(String)
```

この一行を見てほしい。

`class` `Base` `Column` `String` ——**プログラミング言語の骨組み**は英字。
`M配車区分` `配車区分ID` ——**業務の言葉**は漢字。

**字の形そのものが違うから、目が勝手に選り分ける。**

どこまでが仕組みで、どこからが業務なのか。
読む前に、**見た瞬間に分かる。**

英語だけで書かれたコードでは、こうはならない。

```python
class DispatchCategory(Base):
    __tablename__ = "m_dispatch_category"
```

`class` も `DispatchCategory` も `Base` も、全部同じ字種である。
骨組みと業務の言葉が、同じ色に溶けている。
だから人は、単語の意味を一つずつ読んで、分類し直さなければならない。

日本語を混ぜると、その手間が消える。
**目で見ただけで、構造が浮かび上がる。**

そして、ここから先が賭けだった。

> **人間にとって見やすいなら、AI にとっても見やすいはずだ。**

当時、確証はなかった。
だが、筋は通っている。

AI は、人間が書いた膨大な文章を読んで育っている。
人間が読みやすいように整えた形は、
**AI にとっても、意味の切れ目が分かりやすい形であるはずだ。**

日本語ファーストは、愛国的な選択ではない。
**字種が混ざるという、日本語の構造上の利点を、そのまま設計に使った**選択である。

一枚の素朴な HTML は、それを確かめるための実験だった。
そして、思想は正しかった。

**あとは、器を作り直すだけだった。**

AiDiy——AI と DIY。
名前がつく半年前から、志だけは完成していた。

## 第一章 — 二分間の創世（2026年 1月）

半年の沈黙のあと、1月の最後の日。
最初のコミットが刻まれる。

その **2 分後**。

**299 個のファイルが、一度に世界に現れた。**

*(コミット = 変更を記録として確定させること。
プログラマにとっての、日記の一行)*

AGENTS.md。CLAUDE.md。README.md。
`_setup.py`、`_start.py`、`_stop.py`、`_cleanup.py`。
C利用者.py、C採番.py、C権限.py。

この 2 分間が、すべてを説明している。
半年ぶんの設計が、堰を切って流れ出したのだ。

### なんのために、AGENTS.md が最初にあったのか

見逃してはいけない一点がある。

**最初のコミットに、AGENTS.md と CLAUDE.md が入っていた。**

これは「AI への説明書」である。
このプロジェクトが何で、どういう決まりで書かれ、どこに何があるか——
それを人間ではなく、**AI に読ませるために**書かれた文書だ。

コードより先に、AI への手紙が置かれた。

つまり作者は、最初の 2 分の時点で、
**これを人間だけで書くつもりが、まったく無かった。**

### なんのために、DB の自動採番を捨てたのか

`C採番.py`。

普通、データベースの ID は DB に自動で振らせる。
1、2、3……と勝手に増える。楽だし、誰もがそうする。

AiDiy はそれを使わない。
採番専用のテーブルを作り、そこで ID を一元管理する。

面倒な道を、わざわざ選んでいる。

**業務の番号は、業務の都合で決まるからだ。**

「配車番号は年度＋連番」「棚卸は月次でリセット」——
現場にはそういうルールがある。
DB の都合で振られた番号は、その要求に一生応えられない。

*これは、「フレームワークに合わせて業務を曲げない」という宣言だった。*

### なんのために、マイグレーションツールを捨てたのか

Alembic を使わない、という選択も同じ根から出ている。

*(Alembic = DB の設計変更を、履歴として安全に積み上げる道具)*

普通のプロジェクトなら、まず入れる。安全だから。
だが安全と引き換えに、**過去の決定に縛られる。**

AiDiy は、この先の一年あまりにわたって、
何百ファイル単位で作っては壊すことになる。

**壊せる自由を、安全より優先した。**
実験を繰り返す前提の、器の設計だった。

## 第二章 — 声は、最初からいた（2026年 2月）

2月のログは、退屈なほど同じ言葉で埋まっている。

> AIコアを修正。AIコアを修正。AIコアを修正。

記録された 13 日のうち、**12 日**が同じ場所への修正で始まる。
一日 3 ファイルの日もあれば、200 ファイルを超える日もある。
けれど毎日、同じ心臓を叩いている。

AIコアとは、チャットと、音声と、画像と、ファイルと、
6 枚のコードパネルを、一本の通信路で束ねた場所である。

ここが動かなければ、思想は絵に描いた餅で終わる。

### なんのために、二度目の作り直しをしたのか

だが 2月の毎日は、細かい修正の積み重ねではなかった。

**この月、画面はもう一度、ほとんど作り直されている。**

素の JavaScript で書かれていた画面が、
**Node.js と Vue.js の上へ、まるごと移された。**

*(Node.js = ブラウザの外で JavaScript を動かす土台。
Vue.js = 画面の組み立てを助ける枠組み)*

思想は、一文字も変えていない。
日本語のまま通す。共通部分と業務部分を分ける。声を前提に置く。
**変えたのは、器だけである。**

なんのために、動いているものを作り直したのか。

理由は、拍子抜けするほど実務的だ。

**同じことを、もっと短いソースで書けるようにするため。**

素の JavaScript で 100 行かかっていた画面が、
枠組みに乗せれば 30 行で済む。

行数が減ると、二つのことが同時に起きる。

**一つ。速くなる。** 書く量が減るのだから当然だ。

**二つ。壊れにくくなる。**
不具合は、書いた行数に比例して増える。
書かなかった 70 行には、バグが一つも入らない。

これは、あとから効いてくる選択だった。

この先、AI が画面を書くことになる。
**AI が書く量も、同じだけ減る。**
短く書けるということは、AI が見失う余地が小さいということでもある。

序章の一枚は、思想が正しいことを確かめるための実験だった。
2月の作り直しは、**その思想を、長く走れる形に載せ替える工事**だった。

同じ考えのまま、二度作る。
それができるのは、**捨てられる設計にしてあったから**である。

### なんのために、二日目に「声」を作ったのか

プロジェクトが始まって、まだ二日目。
そのコミットに、こんなファイルが並んでいる。

```
audio_processing.py     ← 音を扱う
live_gemini.py          ← Google の音声AIと繋ぐ
live_openai.py          ← OpenAI の音声AIと繋ぐ
+live_tools.py          ← 【新規】喋りながら道具を使う
```

**音声は、後から足した機能ではなかった。**

チャットができてから声をつけた、のではない。
**最初の週から、二種類の音声AIに口をつけている。**

そして `live_tools.py` の「新規」に注目してほしい。

これは、**喋っている最中に、AI が実際に手を動かせる**ようにするための部品だ。

声をかけると返事が返ってくる——それはただの音声チャットである。
声をかけている最中に、AI がファイルを読み、DB を引き、コードを直す。

**声が、そのまま作業になる。**

二日目の時点で、作者はそこを見ていた。

16kHz でこちらの声を拾い、24kHz で返事を鳴らす。
聞く耳と喋る口で必要な帯域が違うから、行きと帰りで数字が違う。
この非対称な水路が詰まりなく流れて、はじめて自然な会話になる。

2月の「毎日 AIコアを修正」の中身は、この配管工事だった。

### なんのために、そこまで声にこだわるのか

答えは、この物語の終着点にある。

キーボードは、訓練された人間のための道具である。
コードエディタも、ターミナルも、Git も、全部そうだ。
**それらを使える人だけが、システムを作れる。**

長いあいだ、それが当たり前だった。
だから業務システムは、業務を知らない人が作り、
業務を知っている人は、できあがったものに文句を言う役だった。

**だが、声は、誰でも持っている。**

配車係が「日曜の配車、こう変えたいんだよね」と喋る。
その言葉が、そのまま届く。
訓練も、翻訳も、要らない。

「ユーザーによるシステム開発」の最終形は、
結局のところ**自然な会話**にしかならない。

だから声は、機能の一つではなく、**前提**として最初に置かれた。

### なんのために、ファイル名まで日本語にしたのか

2月の上旬、ある日を境に、ファイルの名前が一斉に書き換わる。

```
live_gemini.py       →  AIライブ_gemini.py
live_openai.py       →  AIライブ_openai.py
audio_processing.py  →  AI音声処理.py
live_tools.py        →  AI内部ツール.py
```

同じ日、`AIソケット管理.py` が消えて `AIセッション管理.py` が生まれる。
「ソケット」という技術の言葉が、「セッション」という会話の言葉になった。

序章の一行は、テーブル名だけの話ではなかった。
**Python のファイル名にまで及んだ。**

なんのために。

現場の人が「音声がおかしい」と言ったとき、
AI が `AI音声処理.py` を一直線に探しに行けるようにするためだ。
`audio_processing.py` を探すのではない。

**対応表が、要らない。**

思想は、最初の 10 日で、実装のすみずみまで届いていた。

### なんのために、落ち方を記録したのか

2月の半ば、こんな修正が入る。

> 自動復旧機能を改善し、プロセス終了時のクラッシュ時刻を記録する

落ちないようにする、ではない。
**落ちたあと、なぜ落ちたか分かるようにする。**

地味な選択に見える。
だがこれは、のちに AI が**自分でログを読んで自己検証する**ための、
最初の一段だった。

AI に仕事を任せるには、AI が結果を読める形で失敗が残らなければならない。

2月は、派手なことが何も起きなかった月である。
そのかわり、**毎日同じ場所を叩き続けられる体力**が証明された。

## 第三章 — 顔を、持つ（2026年 3月）

3月、流れが変わる。

コード表示の仕組みが、Shiki から Monaco へ置き換えられた。

*(Shiki = コードを綺麗に色づけして見せる道具。
Monaco = VS Code というエディタの心臓そのもの)*

見るための道具から、触るための道具へ。
一度作ったものを、使ってみて、足りないと分かったので捨てた。
**「見る」から「触る」への、静かな移行**である。

そして同じ月、`_setup_avatar.py` と VRM が現れる。

*(VRM = 3D キャラクターの標準形式。日本発の規格)*

**アバターの誕生。**

### なんのために、AIに顔を与えたのか

これは飾りではない。**2月に作った声の、行き先**である。

声だけの対話には、致命的に足りないものがある。

**いま聞いているのか、考えているのか、喋ろうとしているのかが、分からない。**

人間どうしの会話では、それを顔で判断している。
相手が口を開きかけたら、こちらは黙る。
目が泳いだら、まだ考え中だと分かる。

その手がかりが無いと、会話は延々とぶつかり続ける。
「あ、どうぞ」「いえ、そちらこそ」を、機械相手に繰り返すことになる。

だから、背景の透けた 3D の身体を用意した。
返ってくる音声に合わせて口が動き、モーションが乗る。

**自然な音声対話を本気で目指すなら、避けて通れない工程だった。**

### なんのために、同じものを二度作ったのか

3月の後半、アバターは Electron でデスクトップに常駐する身体を得る。

*(Electron = ウェブの技術で、普通のアプリを作る仕組み)*

そしてその同じ週に、**まったく同じものが、普通のブラウザでも動くようにされた。**

二度手間である。なぜそんなことを。

デスクトップに常駐する AI アシスタントは魅力的だ。
だが、インストールが要る。

**インストールが要るものは、「現場の人が気軽に触る」の対極にある。**

情シスに申請して、承認を待って、権限をもらって——
その時点で、思想は死ぬ。

だから、**URL を開くだけで同じ体験が始まる道**が、同時に用意された。

3月は、AiDiy が顔と身体を得た月だった。

## 第四章 — 道具を、AIに渡す（2026年 4月）

4月は、この物語の重心が動いた月である。

### なんのために、AIに記憶の場所を作ったのか

ある日、追加されたファイルは、たった 7 つだった。

`_index.md`、`_最終変更.md`、`新たなCLI追加時の作業手順.md`。

**`_AIDIY/knowledge/` の誕生である。**

それまで、AI に何かを直させるたび、同じ説明を最初からしていた。

「このプロジェクトでは採番はこう」「認証はこう」「Vue のパターンはこう」。
毎回。毎回。毎回。

AI は賢い。だが、昨日のことを覚えていない。

**ならば、覚えておく場所を、外に作ればいい。**

修正が終わるたび、AI 自身が
「次に同じことをする者が読むべきこと」を書き残す。
索引を引けば、過去の成功パターンに辿り着ける。

最初に書かれた知見は二つ。
AI の扱い方と、人間の運用ルール。
**AI と人間、両方の作法が、同じ棚に並べられた。**

これは単なるメモではない。
繰り返してきた実験の結果を、**捨てずに残す仕組み**である。

実験は失敗してもいい。
だが、同じ失敗を二度やるのは、ただの無駄だ。

*「使うほど育つテンプレート」——AiDiy の中心的な主張は、この日に生まれた。*

### なんのために、スキルとメモリーに分けなかったのか

ここで、もう一つの選択がある。見過ごされやすいが、重い。

いま世に出ている AI エージェントの多くは、
AI に何かを覚えさせるとき、**二つの入れ物**を用意する。

**スキル**——やり方の手順。「こういうときは、こう作業せよ」。
**メモリー**——覚えておく事実。「この人はこう呼ぶ」「前回こうなった」。

手順と記憶。二つのアーキテクチャ。
一見、きれいな分類である。

**AiDiy は、その二択を採らなかった。**

`_AIDIY/knowledge/` は、ひとつしかない。

置かれているのは、手順も、判断基準も、注意点も、確認方法も、
**全部まとめて「ナレッジ」**である。

分ける軸は、情報の種類ではない。**触る場所**だ。

```
backend_server,M系マスタ追加手順.md
frontend_avatar,frontend_web,AIコードパネル拡張手順.md
共通,mcp利用による自動ビデオ生成手順.md
```

ファイル名の左側に、関係するモジュールを並べる。右側にトピックを日本語で書く。
それだけの規則で、いま 70 を超える知見が一枚の棚に並んでいる。

なんのために。

**書くときの問いと、読むときの問いが、違うからだ。**

書き終えた AI は迷う。「これは手順だろうか、それとも覚え書きだろうか」。
どちらとも言える。だから、どちらに入れても半分は間違いになる。

一方、読むときの問いは、いつも一つしかない。

> **いまから backend_server を直す。何を知っておくべきか。**

このとき欲しいものに、手順も記憶も区別はない。
「M系マスタはこう足す」も「採番は DB に任せない」も、
**同じ瞬間に、同じ場所から出てこなければ意味がない。**

分けた瞬間、AI は二か所を探しに行くことになる。
そして片方だけ読んで、片方を読み落とす。

序章の一行を思い出してほしい。

**翻訳を消す。対応表を挟まない。**

スキルとメモリーの分類もまた、一種の対応表である。
「この知識はどちらの棚か」を引き直す作業が、毎回そこに発生する。

だから AiDiy は、棚を一枚にした。

**知識を、種類で分けなかった。仕事で分けた。**

### なんのために、AIに目と手を渡したのか

同じ月、`.mcp.json` というファイルが現れる。

**MCP——AI に道具を持たせるための、共通の作法。**

思想はシンプルだ。

**AI にコードを書かせるだけでは、足りない。**

思い出してほしい。人間が何をしていたかを。

コードを直す。→ 画面を開いて確認する。→ DB を覗いて中身を見る。
→ ログを読んでエラーを探す。→ 型チェックを走らせる。

**この「確認」の部分だけが、ずっと人間に残っていた。**

AI は書くだけ書いて「できました」と言う。
本当かどうかは、人間が調べる。
だから結局、人間が全部読む羽目になる。

MCP は、その確認の手段を、AI 自身に渡す仕組みだった。

ブラウザを開かせる。画面を撮らせる。DB を読ませる。
ログを追わせる。型を検査させる。

**AI が、自分の仕事を自分で確かめてから報告してくる。**

これが「未来の開発スタイル」の、決定的な一歩だった。

### なんのために、入口を三つ用意したのか

道具の作り方にも、はっきりした思想がある。

19 個の道具は、ばらばらに置かれてはいない。
**すべて「ツール」としてひとまとめにされ、一つのポートから提供される。**

そのうえで、入口が **三つ**開かれている。

**一つ目。MCP の標準である SSE。**
**二つ目。同じく標準の stdio。**

*(SSE / stdio = AI に道具を持たせるときの、決められた繋ぎ方の作法)*

ここまでなら、行儀のよい MCP サーバーである。
世の AI エージェントは、この二つのどちらかで繋がってくる。

**三つ目が、AiDiy らしい。**

> **同じ道具が、ただの HTTP POST でも呼べる。**

パソコンの中で動いている**どんなアプリからでも**、
決められた住所に一行投げれば、同じ道具が動く。

MCP を喋れなくていい。専用の繋ぎ方を知らなくていい。
Python の小さなスクリプトでも、シェルの一行でも、
画面の JavaScript からでも、他のサーバーからでもいい。

なんのために。

**道具を、AI 専用の持ち物にしないためである。**

MCP は、AI に道具を渡すための規格として生まれた。
だが規格に閉じてしまえば、その道具は
**「MCP を喋れる者だけのもの」**になる。

思い出してほしい。この物語が何を目指していたかを。

**訓練が要るものを、一つずつ減らしていくこと。**

絵を描く。声を合成する。画面を撮る。DB を読む。バックアップを取る。
これらは、AI にとってだけ便利な機能だろうか。違う。
**そのパソコンで動く、あらゆる仕組みにとって便利な機能である。**

だから入口を、規格の外にも一つ開けておいた。

この選択は、のちに効いてくる。

自動でビデオを作る仕組みも、AIタスクも、AIチームも、
必要な道具を **HTTP POST で直接叩いて**動いている。
**AI を経由せずに、道具だけを使える。**

規格に忠実であることと、
規格の外の誰にでも開かれていることは、両立できる。

**AiDiy は、その両方を一つの実装に収めた。**

### なんのために、アクセルより先にブレーキを作ったのか

MCP の直後、差分バックアップの仕組みが追加される。

初回は全部を保存し、以降は変わった分だけを積む。

順番が、すべてを物語っている。

**AI に自由に触らせるためには、まず戻れるようにしなければならない。**

アクセルより先に、ブレーキを作った。
実験を繰り返すための、最後の安全装置がここで揃った。

### なんのために、自分でエージェントを作ったのか

4月の終わり、**1000 を超えるファイル**が一度に追加される。

`cli_main.py`、`run_agent.py`、`agent_loop.py`——

**command_hermes。自前の AI エージェント基盤の統合である。**

claude も copilot も codex も、既に使えていた。
それでも、自分で作った。

なぜか。

他人の道具は、他人の都合で変わる。それもある。
だが、本当の理由はもっと深い。

**エージェントの中身がブラックボックスのままでは、
「未来の開発スタイル」を、自分で設計できない。**

60 を超えるツール。会話が長くなったら中間を自動で要約する圧縮エンジン。
プラグイン。スキルシステム。

——AI エージェントというものを、部品のレベルまで分解して、組み直した。

これもまた、最大級の実験だった。
**「エージェントとは、何でできているのか」を、作ることで確かめている。**

4月、AiDiy は「AI に手伝わせるシステム」から
**「AI が自分で作業できるシステム」**へと変わった。

## 第五章 — 自分を、語りはじめる（2026年 5月）

5月、AI に画像を描かせる道具と、声を合成する道具が加わる。

そして月の半ば、`Xビデオ` というフォルダが生まれた。

そこから月末まで、ログはこの一語で埋まる。
**200、300、500、そして 1300 を超えるファイル。**

### なんのために、自分の紹介動画を作りはじめたのか

シナリオを JSON で書き、シーンごとに HTML を作り、
画像を AI に描かせ、ナレーションを AI に喋らせ、
ブラウザで自動再生する。

**AiDiy は、AiDiy を使って、AiDiy の紹介動画を作りはじめた。**

自分で作った画像生成の道具で絵を描き、
自分で作った音声合成の道具で声を当て、
自分で作ったコードパネルで再生ページを書く。

道具が、道具自身を説明する道具になった。

だがこれは、自己紹介のためだけではない。
**もっと残酷な種類の実験だった。**

> **AI は、20 枚のシーンを、最後まで破綻させずに構成できるか。**

1 シーンの HTML なら、誰にでも作れる。
20 シーン分のナレーションと画像と演出を、
**一本の筋として通しきれるか**は、まったく別の話だ。

長い仕事を、最後まで見失わずにやれるか。
それは、のちに AI へ業務システムの改修を丸ごと任せるための、
**予行演習**そのものだった。

5月の膨大なファイル数は、その答えを得るまでに要した回数でもある。

### そして、ここで一つの発見があった

答えは、期待とは少し違う形で返ってきた。

最初の発想は、素直なものである。
**手順を Python スクリプトとして書き、AI にそれを実装させる。**
あとは実行ボタンを押せば、20 枚の動画が最後まで出来上がる——はずだった。

**ところが、一気には走らない。**

長い手順を一息で流そうとすると、必ずどこかで崩れる。
途中で文脈を見失い、前提を取り違え、あるいは黙って止まる。
何度やっても、同じところで同じように破綻するわけでもない。

原因を探して、作り直して、また流す。
5月の膨大なファイル数の正体は、その繰り返しでもあった。

そして、答えが見つかる。

> **AI が、ステップごとに Python スクリプトを呼ぶ。**

手順そのものはスクリプトの中に書いてある。
だが、それを一息で走らせるのではない。
**一段だけ実行し、結果を確かめ、次の一段を呼ぶ。**

シナリオを作る。確かめる。画像を描く。確かめる。声を当てる。確かめる。
一段ごとに、成果物がファイルとして残る。
崩れたら、その一段だけをやり直せばいい。

すると、**毎回、同じように最後まで到達する。**

これは、思ったより深い発見だった。

AI に長い仕事を任せるとき、必要なのは
「もっと賢い AI」でも「もっと詳しい指示」でもない。

**手順を持つスクリプトと、それを一段ずつ辿る AI。**
その二つに分けた瞬間、実行が安定する。

スクリプトは、道筋を忘れない。
AI は、一段ぶんだけなら見失わない。
**互いの弱点を、互いが埋めている。**

この形は、そのまま持ち越されることになる。

7月に生まれる **AIタスク**——
要求を明細へ分解し、一歩ずつ検証つきで実行する仕組み。
そして **AIチーム**——
動的に組み立てられた手順を、AI がなぞって処理していく仕組み。

**どちらも、この 5月の発見の子どもである。**

動画を作っていたつもりで、
**AI に仕事を任せるための作法そのものを、見つけていた。**

同じ月、配信ソフトと動画変換ツールが AI の手の届く場所に置かれる。
**作るところから、届けるところまでが繋がった。**

## 第六章 — 手元に、灯をともす（2026年 6月）

6月は、静かな月だった。
細かい調整が続く中に、小さな種が蒔かれる。

`local_main.py`。`Gemma`。

**自分のパソコンの中で動く、AI 推論サーバー。**

*(Gemma = Google が公開している、手元で動かせる AI モデル)*

### なんのために、手元で動くAIが要るのか

理由は二つある。

一つ目。

**業務システムは、外に出せないデータを扱う。**

配車先の住所。取引先の単価。従業員の情報。
どれだけ賢くても、クラウドに投げられないものは、投げられない。
これは技術の問題ではなく、信義の問題だ。

二つ目。もっと本質的な理由。

**「未来の開発スタイル」が、API キーと従量課金の上にしか成立しないなら、
それは一部の人のものにしかならない。**

月額を払える会社の、予算を持つ部署の人だけが、
自分の言葉でシステムを作れる——そんな未来に、意味はあるだろうか。

**手元で完結する道が一本も無いなら、DIY とは呼べない。**

そしてこれは、定点観測所でもあった。

手元の PC に載る小さなモデルは、いまどこまでやれるのか。
巨大なクラウドモデルとの差は、半年で、一年で、どれだけ縮むのか。

その物差しを、自分の中に持っておく必要があった。

6月の終わり、AiDiy は
**クラウドなしでも喋れる AI を、自分の中に宿していた。**

## 第七章 — 遊びという名の、計測（2026年 7月・前半）

7月、2400 を超えるファイルの大改造が走る。
そしてなぜか、その同じ日のログに、ゲームの名前がある。

`Xインベーダー`。

続く数週間、こんなフォルダが並んでいく。

```
Xピンボールfable
Xピンボールopus
Xピンボールsol_new
```

**モデルの名前が、そのままフォルダ名になっている。**

### なんのために、ゲームを作ったのか

これは息抜きではない。**計測である。**

ゲームは、AI の実力を測る道具として、ほとんど理想的なのだ。

**仕様が短い。**「インベーダーを作れ」で伝わる。

**なのに中身は重い。**
物理演算、当たり判定、状態遷移、フレームループ、入力処理、スコア管理。
そして「面白いかどうか」という、正解の無い最終判断。

**そして、動かせば一目で分かる。**
テストを書かなくていい。遊べば実力が出る。
ボールが壁にめり込んだら、そこまでだと分かる。

同じ「ピンボールを作れ」を、異なる AI に投げ、
出てきたものを並べて置いてある。

どれが物理をきちんと組めたか。
どれが最後まで完走したか。
どれが、指示に無い気の利いた挙動を足してきたか。

### なんのために、そこまでして測るのか

AiDiy は、6 枚のコードパネルを持ち、
8 種類の AI を自由に割り当てられる。
計画・実行・検証の 3 つの局面には、**別々の AI を指定できる。**

重い思考には賢いモデル。単純な作業には速いモデル。
——そう設計されている。

**では、どのモデルが、どの局面に向いているのか。**

カタログには書いていない。
公開されているスコアも、実務の役には立たない。

知る方法は、ひとつしかない。

**同じ課題を投げて、出てきた実物を、並べて見比べることだ。**

7月前半は、そのための時間だった。
そして測定が済んだからこそ、次に来るものが作れた。

## 第八章 — 群れに、なる（2026年 7月・後半）

### なんのために、AIに仕事の分解を任せたのか

7月、`tasks` という名前がログに現れる。

**AIタスクの誕生。**

これまで、AI に仕事をさせるには、人間が指示を分解する必要があった。

「まずここを直して」「次にこれを追加して」「最後に確認して」。

**分解する人間が、結局ボトルネックになる。**

どれだけ AI が速くても、指示を刻む人間の速度以上には進めない。
これでは「現場の人が話しかけるだけ」には、永遠に届かない。

**ならば、分解そのものを AI にやらせればいい。**

要求を放り込むと、AI がプロジェクトを実際に読み、
開始・処理・終了の明細へと自分で割る。

しかも分解は 2 段構え。
**第 1 段が中身を考え、第 2 段が決まった形式に清書する。**

これは 7月前半の計測から得た知見の、直接の応用だった。

> **賢いモデルは形式を破る。従順なモデルは中身が薄い。**

なら、賢い方に考えさせて、従順な方に整えさせればいい。
ゲームを並べて見比べた経験が、そのまま設計になった。

### なんのために、タスクを一列に並べなかったのか

分解された明細は、一列には並ばない。

それぞれが「自分より先に終わっているべき明細」を、複数指定できる。

*(つまり、作業の依存関係が「網」になる)*

カンバンの固定列でもなく、垂直の流れ作業でもない。
**水平に枝分かれして、走れるものから同時に走る。**

そして、いちばん時間のかかる経路が、
**クリティカルパス**として図に描かれる。

なぜここまでするのか。

現実の改修は、一直線ではないからだ。
「DB を直す」「API を直す」「画面を直す」——
DB が終われば API と画面は同時に進められる。

**人間のチームが当たり前にやっていることを、AI にもさせる。**

### なんのために、一歩ずつしか任せないのか

実行の作法には、強い思想がある。

開始の明細は、AI を使わない。**ただバックアップを取る。**
処理の明細は、**一歩だけ**を AI に渡す。
検証を付ければ、AI 自身の報告を確かめ、
何も書かれていない・エラーが出た時だけ、**一度だけ**やり直す。
終了の明細が、最終確認をする。

「AI に全部任せる」ではない。

**「AI に、検証つきで、一歩ずつ任せる」。**

これは、何度も投げて何度も外した経験からしか出てこない設計である。

そして、その経験の出どころは、はっきりしている。
**5月、動画を一気に走らせようとして、何度も崩れたあの日々だ。**

手順を持つスクリプトと、それを一段ずつ辿る AI。
動画で見つけたその形が、ここでは業務システムの改修に向けられている。

### なんのために、AIをチームにしたのか

7月の下旬、`persona`、`要員` という言葉が現れる。

**AIチームの誕生。**

依頼を登録すると、AI が担当を選ぶ。

選ぶ材料は、登録された要員と、
**その要員が過去に貯めた経験**——経験値、得意分野、直近の学び。

経験のある者に仕事が寄っていく。
だから、貯めたノウハウが、そのまま次に使われる。

チームは 2 種類の回し方を持つ。
**PlanDo**（計画 → 実行）と、
**SPDCA**（相談 → 計画 → 実行 → 評価 → 改善）。

ここに、厳しい掟がある。

> **ソースを書き換えていいのは、実行(D)だけ。**
> 評価(C)と改善(A)は、読むことと試すことに徹する。

**評価する者に、書き換えを許さない。**

人間の組織が長い時間をかけて学んだ規律を、AI にも課している。
自分の仕事を自分で採点すれば、甘くなる。それは人でも AI でも同じだ。

そして、自動作業をオンにすると——

数分おきに、要員が一人ずつ「いま何をやるべきか」を発言する。
ただの雑談ではない。**プロジェクトのソースを実際に読んでから**喋る。

意見が半数を超えたところで、まとめ役の人格が、
それをチームの作業へと束ねる。

**AI たちが、勝手に相談しはじめる。**

依頼が終わると、AI が自分の作業記録を読み直し、
経験値と学びを生成して、経験テーブルに書き込む。
次の依頼の担当選びが、その経験を参照する。

**回すほど、適材適所になっていく。**

7月前半、人間がやっていたこと——
複数の AI に同じ課題を投げ、出来を見比べ、得意分野を覚えておくこと。

**7月後半、システムそのものが、それを行うようになった。**

ピンボールを並べていた手つきが、そのまま AIチームの頭脳になった。
4月に生まれた「知見フォルダ」は、
7月には **AI 自身の経歴**として実装されていた。

## 第九章 — 地層を、厚くする（2026年 8月）

8月、6月に蒔いた手元 AI の種が、**2000 を超えるファイル**の本体になる。

そして同じ月、静かだが重い変化があった。

**テストコードが書かれはじめた。**

### なんのために、いまテストなのか

壊して作り直すことを続けるなら、
**「前は動いていたのに」を自動で見つける仕掛け**が要る。

実験を繰り返す文化に、ようやく安全網が張られた。
速く走るためではない。**速く走り続けるため**である。

同じ月、知見フォルダが一斉に書き直される。

`M系マスタ追加手順`、`S系スケジューラ追加手順`、
`T系トランザクション追加手順`、`V系エンドポイント追加手順`——

**7 つの系統それぞれに、「新しい業務機能の足し方」が文書化された。**

これは、AiDiy がテンプレートとして成熟した瞬間である。

配車も生産も在庫も、もはや「サンプル」ではない。
**同じ手順で、会計にも人事にも顧客管理にも伸ばせる「型」**になった。

月の半ば、奇妙なコミットがある。

歴史ファイルそのものが、**いったん全部消されて、作り直されている。**

自分の来歴を、より良い形で記録し直したかったのだろう。
いまこの文書が読んでいる記録は、その日に生まれ変わったものだ。

**歴史すら、実験の対象だった。**

## 第十章 — 現在地（2026年 9月）

あの夏から、一年あまりが過ぎた。

2025年の夏、FastAPI と HTML と JS だけの一枚のページから、
いま AiDiy はこうなっている。

**5 つのサーバーが、同時に立つ。**
業務の中核、業務アプリ、AI の道具箱、手元の推論、タスクとチーム。
それを、利用者からは「ひとつ」に見えるよう束ねてある。

**19 個の道具が、AI の手の中にある。**
ブラウザを操り、画面を撮り、DB を読み、ログを追い、型を検査し、
バックアップを取り、絵を描き、動画を作り、声を聞き、声を出し、
配信を回し、動画を変換し、音で知らせ、
他の AI を呼び、タスクを投げ、チームに依頼し、パソコンを操作する。

**8 種類の AI が、6 枚のパネルで並走する。**

**そして日本語が、DB から画面まで、一本で通っている。**

```
Table : C利用者          Column : 利用者ID
API   : POST /core/利用者/一覧
JSON  : { "利用者ID": "admin" }
File  : C利用者一覧.vue
```

どこにも翻訳がない。
**現場の人が口にした言葉と、DB に立っている名前が、一字一句同じである。**

序章で立てた一行への、この一年あまりぶんの答えがこれだ。

そして、自己検証の輪が回る。

> **コードを直す → DB で結果を見る → ログでエラーを見る → 型で再確認**

**AI が、自分で確かめてから報告してくる。**
人間は、指示と判断に集中する。

実験区画には、いまも過去の実験が残っている。
ハローワールド、太陽系、インベーダー、3 種類のピンボール。

**捨てられていないのは、それが記録だからだ。**
4月の AI にはここまでできた。7月にはここまでできた。
そのスナップショットが、フォルダとして地層になっている。

## 終章 — 目指すべき、未来の姿

**未来の開発スタイルとは、何か。**

人間が仕様を書き、AI がコードを書く——ではない。
それはまだ、ただの分業だ。

AiDiy がこの一年あまりをかけて出した答えを、
一つの朝の風景として描いてみたい。

---

朝、配車係が席につく。
画面の隅に、アバターが立っている。

コードエディタは開いていない。ターミナルも、Git も、開かない。
彼は、こう言う。

> **「日曜の配車さ、いま区分が一つしかないけど、
> 午前と午後で分けたいんだよね。担当も別だし」**

それだけだ。仕様書も、チケットも書かない。
`M配車区分` という単語すら、口にしなくていい。

アバターが頷く。口が動く。

> **「配車区分を午前・午後に分けて、担当者も分ける、ですね。
> いまの日曜の配車、37 件ありますが、これはどちらに寄せますか」**

**AI は、DB を実際に見てから聞き返している。**
会話の裏側で、道具が静かに走っている。

> **「午前でいいよ。あ、でも 15 時以降のは午後で」**

彼が答えたその瞬間、AI は仕事を分解しはじめる。

バックアップを取り、`M配車区分` にレコードを足し、
`T配車` に列を足し、`S配車_週表示` の描画を直す。
一歩ごとに、ログと型で確かめながら。

数分後、アバターが顔を上げる。

> **「できました。日曜の週表示、午前と午後でレーンが分かれています。
> 既存の 37 件は、14 件が午前、23 件が午後に入りました。
> 画面、見てもらえますか」**

彼は画面を見る。合っている。
それで、終わりだ。

---

**この一連に、翻訳が一度も挟まっていない。**

彼が言った「配車区分」は `M配車区分` として立ち、
彼が言った「午前」は `午前` というデータとして入り、
彼が見た画面は `S配車_週表示.vue` が描いている。

どこにも `dispatch_category` は出てこない。

そして彼は、**キーボードを一度も触っていない。**

### 四つの必要条件

この朝を成立させるために、必要なものは四つある。

| | なんのために |
|---|---|
| **自然な音声対話** | 訓練の要らない、唯一のインターフェースだから |
| **日本語ファースト** | 声に出した言葉が、そのままコードの言葉になるため |
| **自己検証** | AI が自分で確かめてから報告するため |
| **経験の蓄積** | 次に同じことを頼んだとき、もっと速いため |

この四つは、別々の機能ではない。
**一つの体験を成立させるための、四つの必要条件**である。

音声だけあっても、コードが英語なら翻訳が挟まる。
日本語だけ通っても、AI が確かめずに報告すれば信用できない。
確かめても覚えなければ、明日また同じ説明をすることになる。

**だからこの一年あまり、全部を同時に作った。**

## 展望 — これから、起こりうること

ここから先は、まだ実現していない。
だが、いまある部品の延長線上に、確かに見えているものがある。

### ◆ 「言えば直る」が、日常になる

いまはまだ、要求を投げて数分待つ。

だが AI の推論は、測るたびに速くなっている。
去年 3 回やり直しが要ったことが、今年は 1 回で済んでいる。

やがて、**喋り終わる頃には終わっている**日が来る。

そのとき、業務システムは「導入するもの」ではなくなる。
**毎日少しずつ言葉で削られ、足されていく、生き物になる。**

### ◆ 現場の言葉が、そのまま会社の資産になる

AIチームは、依頼が終わるたびに経験を書き込む。
知見フォルダには、修正のたびに学びが積まれる。

これが 3 年続いたら、何が起きるか。

**「あの人しか分からない」が、消える。**

ベテランが退職しても、その人が AI と交わした会話と、
そこから生まれた判断の記録が、テーブルに残っている。
新しく入った人が「これ、なんでこうなってるの」と聞けば、
AI は当時の経緯を読んで答えられる。

属人化という、日本の業務システム最大の病に、
**構造で効く薬**になりうる。

### ◆ 手元の AI が、クラウドに追いつく

手元で動くモデルは、この 1 年で劇的に軽く、賢くなった。
その差は、まだ縮み続けている。

やがて、**社内のパソコン一台で、全部が完結する**日が来る。

外に出せないデータを持つ会社。
ネットワークが繋がらない工場。海の上の船。

**そこでも、話しかけるだけでシステムが育つ。**

「予算のある会社だけの未来」にしないための備えは、
もう 6 月に打ってある。

### ◆ 道具が増えれば、AI の手が伸びる

19 個の道具は、設定ファイルに一行足せば増やせる。

倉庫のバーコードリーダー。工場のセンサー。POS レジ。
電話の音声ログ。メールの受信箱。会計システム。

**繋いだ分だけ、AI が「見て、触れる」範囲が広がる。**

そのとき AI は、こう言えるようになる。

> 「先週から C ラインの不良率が 1.8% 上がっています。
> 原因は 3 号機の温度設定かもしれません。
> 検査項目を一つ増やしましょうか」

**聞かれる前に、気づいて提案する。**
道具が増えるとは、そういうことだ。

### ◆ 業務の種類が、横に広がる

配車・生産・在庫は、もう「型」になっている。
同じ手順で、会計にも、人事にも、顧客管理にも伸ばせる。

そしてその型は、**言葉で複製できる。**

「うちの業界の受注管理を作りたい」と話しかければ、
既存の型を読んだ AI が、その業界の言葉で組み直す。

**業種ごとのテンプレートが、会話から生まれる。**

### ◆ 日本語ファーストは、日本語だけの話ではない

この設計思想の核心は、「日本語」ではない。

**「利用者の母語と、コードの語彙を、一致させる」**ことだ。

だから、そのまま他の言語へ移せる。

タイの物流会社は、タイ語のテーブル名で。
ブラジルの工場は、ポルトガル語のカラム名で。

**世界中の現場の人が、自分の言葉のまま、自分のシステムを持てる。**

英語ができる人だけが作れる時代を、終わらせる。

### ◆ AI が世代交代しても、設計は死なない

新しい AI は、これからも出続ける。
去年の常識は、来年には古びる。

だが AiDiy には、実験区画がある。

新しいモデルが出たら、同じ課題を投げて、並べて見比べる。
向いている局面に差し替える。

**AI が入れ替わっても、この仕組みは生き続ける。**

測りつづける文化を持っていることが、
実は**いちばん長く効く投資**なのかもしれない。

### ◆ そして、テンプレートは分かち合える

非商用のライセンスのもと、
誰かが作った業務テンプレートを、別の誰かが引き継ぐ。

配車の型を、隣の県の運送会社が使う。
その会社が育てた改良を、また別の誰かが受け取る。

**現場の知恵が、コードの形で流通しはじめる。**

そのとき「ユーザーによるシステム開発」は、
一人の DIY を超えて、**みんなの DIY** になる。

## 付記：この物語の典拠

**記録に残っているもの**

- 各月の出来事、ファイル数、コミットメッセージ、ファイル名
  → `_AIDIY/histories/`（2026年1月〜9月、130 日分）
- 現在の構成と数値（5 サーバー / 19 MCP / 8 CLI / 7 系統 など）
  → `frontend_web/public/X自己紹介/index.html`
- スキルとメモリーに分けず、ナレッジを一枚の棚に統合したこと、
  および `対象モジュール,トピック名.md` という命名規則
  → `_AIDIY/knowledge/_index.md`

**作者の証言によるもの**

- 2025年8月の前身（FastAPI + HTML + JS のみ、実装は同一）
- その前身の時点で、すでに複数サーバー構成と、
  業務システムの共通部分・個別アプリ部分の分離が実装されていたこと
- 2026年2月に、思想は変えないまま Node.js + Vue.js へほぼ作り直したこと。
  目的が、フレームワーク利用による短いソースへの移行——
  すなわち生産性の向上と不具合の抑止であったこと
- MCP を tools としてまとめ、標準の SSE / stdio に加えて、
  localhost 上のあらゆるアプリから使える HTTP POST の入口を
  同じ実装に統合したこと（`backend_tools/tools_main.py`、ポート 8095）
- 主題が「未来の開発スタイルの追究」「ユーザーによるシステム開発」であること
- 日本語ファーストの根拠が「日本語で AI と会話するなら、変数名も日本語であるべき」であること
- 目指す姿が「自然な音声対話による開発」であること
- 実験的実装を繰り返す方法をとってきたこと
- ゲーム開発が、その時点の AI 性能を把握する手段であったこと

**推察・創作であるもの**

各機能が「なんのために」追加されたのか——
その動機づけの多くは、変更されたファイルの並びと順序、
そして到達点から**逆算した推論**である。

たとえば「2月に毎日 AIコアを叩いていた理由」
「ゲームの計測が AIタスクの 2 段分解に繋がったという因果」
「テストが 8月に書かれた理由」は、記録に明言はない。

終章の朝の風景、および「展望」章の全体は、
現在の実装から考えられる**未来の姿の描写**であり、
実現済みの機能ではない。

章題・場面描写・心情も創作である。
月・数値・固有名詞は、記録どおりとした。
